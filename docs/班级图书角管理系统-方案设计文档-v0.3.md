### 本版修订摘要（v0.2 → v0.3）

评审方补充：**米兔手表只装 1 台，戴在图书管理员（学生）手腕上**。这一条推翻了 v0.2 的一个核心前提，影响面很大：

| # | 变更 | 性质 |
|---|---|---|
| 1 | **撤回 v0.2 的核心洞察**"手表自带身份 → 借书只需扫一次" | **失效**。一台手表只能代表一个人，借书仍需要选人，该结论不成立 |
| 2 | **手表端定位重构**：从"45 台学生个人终端"改为"**1 台管理员随身工作终端（PDA）**" | **重定位**。价值场景从"学生自助借书"变为"移动盘点 / 现场还书 / 理架查书 / 巡场催还" |
| 3 | **Q1×Q3 的架构冲突基本消解**：1 台固定设备可直接连教室 WiFi，**隧道从"必须"降为"备选"** | **大幅简化**。零成本、零公网暴露面 |
| 4 | **权限风险上升**：手表从学生只读终端变成能改账的管理员终端，丢失即等于钥匙丢失 | **新增风险**。新增设备锁、短令牌、远程吊销、敏感操作禁用等 6 项措施 |
| 5 | **提醒能力进一步削弱，但换来更强的替代**：学生不再收到个人提醒；改为管理员**巡架主动催还** | **有得有失**。已明确写入 5.3.4 |
| 6 | S7 工期由 4–10 天降至 **2–4 天**，且整体可裁剪 | **降本** |

> v0.1（初稿）、v0.2（落实 Q1–Q4）保留在同一目录，供对照追溯。

### v0.2 修订摘要（v0.1 → v0.2）

已落实评审方对 Q1–Q4 的答复，以下五处发生**实质性变更**（非文字调整）：

| # | 变更 | 起因 | 影响范围 |
|---|---|---|---|
| 1 | **发现并解决 Q1×Q3 的架构冲突**：本地部署 + 4G 手表 = 手表无法访问服务端。新增「轻隧道 + 路径白名单」方案 | Q1 + Q3 组合 | 3.2、5.3、6.3、新增 R11 |

## 3. 设计原则与总体架构

### 3.1 六条设计原则

| 编号 | 原则 | 具体含义 | 落地体现 |
|---|---|---|---|
| P1 | **单一真相源** | 服务端是唯一写入口，三端之间**不互相同步**，全部与服务器同步 | 从架构上消灭"端到端冲突"这一整类问题 |
| P2 | **扫码优先，点击最少** | 核心动作 ≤ 3 步、≤ 10 秒完成 | 管理端借书 = 点头像 + 扫书码；**手表借书 = 扫书码 + 点确认** |
| P3 | **账实分离，流水为证** | 副本状态是"当前态"，借阅单是不可变流水；任何状态都可由流水重算 | 数据出问题时可回溯、可修复 |
| P4 | **规则参数化** | 借期、上限、续借次数、提醒节奏全部可配置 | 换班级、换学期不用改代码 |
| P5 | **可降级** | 断网能借、没扫码枪能手输、手表不可用能代借、没系统能纸记 | 保证极端情况下业务不中断 |
| P6 | **最小权限 + 全程留痕** | 学生图书管理员是"操作员"而非"管理员" | 所有写操作进审计日志，30 秒内可撤销 |

**关键架构决策说明（v0.3 修订）：**

1. **三端不互联，只连服务端**。手表、手机、网页之间没有任何点对点通道，因此不存在"设备 A 与设备 B 谁的数据对"的问题，冲突只可能发生在"端 vs 服务端"。
2. **首选局域网，公网暴露面归零**。v0.2 里"必建隧道"的结论已不成立——只有 1 台手表，让班主任协调把它接进教室 WiFi 是完全可行的。**能走局域网就不要开隧道**，这是本版最重要的简化：零成本、零备案、零公网攻击面。
3. **推送是纯出站**，与网络拓扑无关。到期提醒由服务端主动出站调用推送服务，即使教室完全断外网，也只是推送失败，账目不受影响。
4. **手表端的写入受服务端完全约束**。手表提交还书/盘点请求后，所有校验在服务端完成，手表只负责展示结果，不得自行判定成功。
5. **手表权限等级上升，必须按"管理员设备"来防**。v0.2 的手表是学生只读终端，丢了影响有限；现在它绑定的是图书管理员，能做账务变更。6 项防护措施见 5.3.3。

**手表端的上线顺序（v0.3 简化，不再分 L0/L1）**

| 步骤 | 能力 | 依赖 | 阶段 |
|---|---|---|---|
| 第一步 | 到期/逾期提醒推送（推给管理员，含名单） | 仅出站，**零网络改造** | S5 |
| 第二步 | 扫码查书 + 现场还书 + 移动盘点 | 需手表能访问主机（WiFi 或隧道） | S7 |

> 因为全程在局域网内，v0.2 那套"L0 不需要隧道 / L1 需要隧道"的分级已经没有必要——两步都只需连上 WiFi。

### 3.3 三端能力分级

| 端 | 定位 | 主要使用者 | 典型场景 | 能力上限 |
|---|---|---|---|---|
| **Web 管理端** | 全功能工作台 | 班主任、图书管理员 | 教室一体机上录入、盘点、看报表 | 全部功能，含配置/导出/审计 |
| **移动端** | 管理员随身操作 + 学生共用视图 | 图书管理员（手机/平板） | 课间在书架旁扫码借还；学生点选头像查自己的借阅 | 借还、查询、续借、盘点扫码；**不含系统配置与权限管理** |
| **手表端（仅 1 台）** | **图书管理员的随身工作终端（PDA）** | 图书管理员（学生，1 人） | 沿书架扫书盘点；同学还书时现场扫一下；理架时查"这本是谁借的" | 扫码查书、现场还书、移动盘点、今日待办、提醒推送；**不含**检索列表、图书详情长文、统计、成员管理、规则配置 |

> **手表端的定位变化（v0.3）**：v0.2 曾把手表设想成"全班 45 人每人一台的个人终端"，并由此推导出"借书只扫一次"的效率优势。改为**只装 1 台、归图书管理员**后，这个前提不再成立——一台手表只能代表一个人，而借书必须知道"借给谁"。手表因此回到更朴素也更站得住的定位：**一支戴在手腕上的扫码枪 + 一台微型 PDA**。详见 5.3.1。

## 4. 功能模块划分

### 4.1 模块总览

| 编号 | 模块 | 一句话职责 | 拥有（Write） | 只读（Read） |
|---|---|---|---|---|
| M1 | 图书录入与分类 | 把实物书变成系统里可管理的条目 | book、copy、category | — |
| M2 | 检索与浏览 | 让人找到书 | 无（纯只读） | book、copy.status |
| M3 | 借阅 / 归还 / 续借 | 唯一能改变"谁拿着哪本书"的模块 | loan、copy.status | user、book、setting |
| M4 | 逾期提醒 | 把"该还了"送到人手上 | reminder | loan、setting |
| M5 | 库存盘点 | 账实核对，产出差异单 | inventory_session、inventory_item | copy、loan |
| M6 | 成员与权限 | 管人、管角色、管授权 | user、role_grant | — |
| M7 | 借阅统计 | 把流水变成可读的报表 | 无（纯只读聚合） | 全部（只读） |
| X1 | 数据同步与离线 | 保证端与端之间账目一致 | op_log | 全部 |
| X2 | 审计日志 | 谁在什么时候改了什么 | audit_log | — |
| X3 | 系统设置与备份 | 规则、备份、健康检查 | setting | — |

> **核心原则**：每一类数据只有**一个模块**拥有写权限。跨模块需要变更时，通过调用对方的能力完成，不允许直接写表。这条规则是模块边界能守住的关键。

### 4.2 M1 图书录入与分类

**职责**
- 书目信息建档：ISBN、书名、作者、出版社、封面、简介、适读年级、字数
- 副本管理：为一本书生成 N 册副本，每册生成唯一条码，记录存放书架位置
- 分类体系维护：班级自定义二级分类 + 标签（注音版 / 绘本 / 章节书 / 科普…）
- 批量导入：从 Excel 一次性导入既有书单
- 下架与注销：书籍丢失、破损严重、淘汰时移出流通

**边界（不做什么）**
- ❌ **不负责副本的在架/借出状态**。状态归 M3 所有，M1 只能读。
- ❌ **不能直接删除有未还借阅的副本或书目**。必须由 M3 先结清，或走"丢失登记"流程。
- ❌ 不做借阅规则判断（额度、期限归 M3）。
- ❌ 不做"推荐这本书给谁"（属 M7 的扩展能力，一期不做）。

**关键规则**
- 书目与副本**必须分离**：同一种书 5 册 = 1 条 book + 5 条 copy。这是盘点、借还、统计正确性的基础（详见 7.3）。
- 副本条码全局唯一，且**打印后不可复用**。副本注销后条码作废，不再分配。
- 分类采用班级自定义，不套用中图法——小学生和图书管理员都不需要 22 个大类。

### 4.3 M2 检索与浏览

**职责**
- 关键词检索：书名 / 作者 / 拼音首字母 / 标签
- 分类浏览：按分类色块进入，封面网格墙展示
- 扫码直达：扫书上的码直接跳详情
- 状态过滤：只看"在架可借"、只看某分类、只看某年级适读

**边界**
- ❌ **纯只读模块，不写任何数据**。
- ❌ 不做个性化推荐算法（一期）。"猜你喜欢"用规则替代：同分类随机 + 同类目高借阅。
- ❌ 不做全文检索（简介全文搜索），数据量太小，模糊匹配足够。

**关键设计（小学生友好）**
- 小学生**不搜索，他们"逛"和"扫"**。因此检索页默认不是空白搜索框，而是「6 个分类色块 + 封面墙」。
- 支持拼音首字母（如输入 `xlsw` 命中《夏洛的网》），因为低年级学生拼音输入慢、易错。
- 无封面图书用「色块 + 书名首字」占位，保证网格整齐。

### 4.4 M3 借阅 / 归还 / 续借

**职责**
- 借出：校验规则 → 创建借阅单 → 变更副本状态
- 归还：按书码匹配未结借阅单 → 结单 → 恢复副本状态
- 续借：延长到期日，次数受限
- 逾期判定：**逾期是计算属性**（`due_at < now 且 status = active`），不单独存状态字段，避免状态陈旧
- 撤销：30 秒内可撤销刚提交的借还操作
- 丢失/破损登记：把副本从流通中摘除并结单

**边界**
- ✅ **本模块是唯一能修改 `copy.status` 和创建 `loan` 的模块**。M1、M5 都不得直接改副本状态。
- ❌ 不负责"提醒怎么发出去"——只把逾期事实暴露给 M4，投递归 M4。
- ❌ 不做成员身份校验的实现（调用 M6），只做权限点判断。
- ❌ 不涉及金额、押金、赔偿计算（A7）。

**关键规则**

| 规则项 | 默认值 | 可配置 |
|---|---|---|
| 借期 | 14 天 | 是 |
| 单人同时在借上限 | 3 册 | 是 |
| 续借次数上限 | 1 次 | 是 |
| 续借延长 | 7 天 | 是 |
| 逾期禁借阈值 | 逾期 ≥ 7 天暂停新借 | 是 |
| 续借前置条件 | 当前未逾期 + 未达次数上限 + 该书无人预约 | 部分 |

**状态机**

副本状态（Copy.status）：

```
                 ┌──────────────┐
   入库 ────────► │  available   │ ◄──────── 归还/续借完成
                 │  （在架可借）  │
                 └──┬────────┬──┘
                    │借出     │下架/淘汰
                    ▼        ▼
              ┌──────────┐  ┌───────────┐
              │ borrowed │  │  retired  │（已注销，条码作废）
              └──┬───┬───┘  └───────────┘
        归还     │   │ 丢失/严重破损
                 ▼   ▼
        available  ┌────────┐   修复    ┌───────────┐
                   │  lost  │──────────►│ repairing │──┐
                   └────────┘           └───────────┘  │
                        ▲                     │修复失败  │
                        └─────────────────────┘         │
                                          修复成功 ──────┘► available
```

借阅单状态（Loan.status）：

```
  active ──归还──► returned（结单，终态）
    │
    ├──续借──► active（due_at 延后，renew_count + 1）
    │
    └──丢失登记──► lost（结单，副本转 lost）
```

> `overdue` 不是 Loan 的状态值，而是 `active + due_at < now` 的派生视图。为提升列表查询性能，可增加冗余字段 `is_overdue`，由每日任务刷新，仅用于筛选加速——**真相始终是 `due_at`**。

### 4.5 M4 逾期提醒

**职责**
- 按规则生成提醒任务（到期前 3 天 / 1 天、逾期当天、逾期后每 7 天）
- 多通道投递：班级大屏（学生侧）、纸质书签、管理员手表（工作提醒）（v0.3：学生侧推送已无通道）
- 去重：同一借阅单同一类型只发一次
- 投递失败重试与降级（微信失败 → 次日并入大屏）

**边界**
- ❌ **不判断是否逾期**。逾期判定归 M3，M4 只消费 `due_at` 与 `status`。
- ❌ 不做催还的"人工沟通"（那是老师的事），只做通知投递。
- ❌ 不修改借阅单状态。学生"已还书"由 M3 结单，M4 收到事件后停止后续提醒。
- ❌ 免打扰时段（21:00–07:00）内不投递，顺延至次日 07:30。

**提醒矩阵**

| 触发 | 提前量 | 通道 | 文案要点 |
|---|---|---|---|
| 即将到期 | 到期前 3 天 | 班级大屏 | "《XX》还有 3 天到期，记得带回学校" |
| 即将到期 | 到期前 1 天 | 班级大屏 + **管理员手表工作提醒** | 学生看大屏，管理员收汇总 |
| 逾期 | 逾期第 1 天 | 班级大屏晨间榜 + 管理员手表 | "已逾期 1 天"，管理员据此巡架催还 |
| 逾期 | 每 7 天 | 班主任汇总 + 管理员手表名单 | 汇总进"本周需处理"清单 |
| 实体兜底 | 借出时 | **纸质书签** | 书签上印"请在 X 月 X 日前还"，随书夹入 |
| 汇总 | 每周一 08:00 | 班主任 | "本周到期 N 本，涉及 M 人" |
| 大屏 | 每日 08:00 | 班级一体机 | 今日应还名单（姓名 + 书名） |

### 4.6 M5 库存盘点

**职责**
- 建立盘点单，选择范围（全库 / 某分类 / 某书架）
- 生成"应有清单"快照（把范围内每册的预期状态写入盘点明细）
- 逐册扫码，实时显示"已扫 / 应扫 / 缺失"
- 结束盘点，生成差异单（缺失 / 错架 / 多余）
- 差异逐条处置：在别处找到 → 改书架位置；确认丢失 → 触发 M3 的丢失登记

**边界**
- ❌ **盘点本身绝不修改副本状态或书架位置**。它只产出"差异单"。
- ❌ 差异处置是独立动作，**需班主任确认**后执行，且执行时调用 M3/M1 的能力，不直接写表。
- ❌ 不做 RFID 批量读取（成本过高，超出班级预算）。
- 支持"边扫边停"：盘点单可跨天保持 open 状态。

**流程**

```
建单(选范围) → 快照应有清单 → 逐册扫码 → 实时看板 → 结束盘点
                                                      ↓
                                              差异单(missing/misplaced/extra)
                                                      ↓
                                       逐条处置（班主任确认）
                                    ↙            ↓             ↘
                          在别处找到→改位置   确认丢失→M3登记   无异常→归档
```

### 4.7 M6 成员与权限

**职责**
- 成员档案：姓名、学号、角色、状态（在班 / 离班）
- 身份体系：学生无账号，靠"共用设备点选"临时进入；手表靠 `device_token` 设备绑定（v0.2）
- 角色分配：学生、图书管理员、班主任
- 临时授权：给某学生开放 N 小时的管理员权限（如值日生）
- 权限点校验：所有 API 的统一入口

**边界**
- ❌ **不管业务规则**。借阅额度、借期属于 M3 的规则配置，M6 只负责"谁有权改规则"。
- ❌ 不存家长手机号、身份证、住址。Q2 取消家长端后，系统**完全不采集任何家长信息**。
- ❌ 不做学生成绩、考勤等其他班级管理功能（避免系统膨胀）。
- ❌ 不提供"删除用户"，只有"置为离班"——历史借阅账目必须保留。

### 4.8 M7 借阅统计

**职责**
- 基础指标：在借总量、逾期总量、今日借还笔数、本月借阅人次
- 排行：图书借阅 TOP10、分类借阅占比、月度阅读之星
- 健康度：零借阅图书清单（用于淘汰或推荐）、平均借阅时长
- 导出：xlsx / csv，供班主任写总结或家长会使用

**边界**
- ❌ **纯只读聚合，不做任何写操作**。
- ❌ 不做预测（"谁可能逾期"）、不做学生画像。
- ❌ **不生成负面榜单**。不公布"借书最少的学生"，只公布正向激励榜单——这是小学场景的伦理底线，也避免家长反感。
- ❌ 不做跨班级横向对比（一期）。

## 5. 角色与核心业务流程

### 5.1 角色定义

| 角色 | 现实身份 | 系统定位 | 关键约束 |
|---|---|---|---|
| **学生** | 全班同学 | 读者 | 只能操作"自己的"数据；不能执行借还（除非临时授权） |
| **班级图书管理员** | 2–3 名高年级学生轮流 | 操作员 | 能借还、录入、盘点；**不能改规则、不能删成员、不能看审计日志** |

> **一句话概括这张表**：手表能"查、还、盘"，但**不适合"借"**——因为借书需要在 45 个人里挑一个，而 1.4 英寸屏放不下这个选择。

#### 5.3.1 定位修正：v0.2 的核心洞察失效（v0.3）

v0.2 曾基于"45 台学生手表"推导出一个结论：

> ~~管理端借书要扫两次（学生 + 书），手表借书只要扫一次（书）——因为手表天然知道"我是谁"。~~

**该结论随本轮前提变更而失效，明确撤回。** 原因很简单：

| 前提 | 手表代表谁 | "借给谁"能否确定 | 结论 |
|---|---|---|---|
| v0.2：45 台，人手一台 | 持表人本人 | ✅ 手表即身份 | "只扫一次"成立 |
| **v0.3：1 台，管理员持有** | 图书管理员 | ❌ 仍要在 45 人中选 | **"只扫一次"不成立** |

一台手表只能代表一个人。当它代表的是管理员时，"借给谁"这个问题仍在，而手表屏无法承载 45 人的选择。

**新的定位**：这台手表服务于**图书管理员**，角色等同于"一支戴在手腕上的扫码枪 + 一台微型 PDA"。

它真正的价值不在"借书"，而在**必须离开座位、在书架之间走动的三个场景**：

| 场景 | 现在的做法 | 用手表 | 收益 |
|---|---|---|---|
| **盘点** | 搬笔记本/平板到书架前，或抄书号回来录入 | 沿书架走，扫一本记一本，进度实时同步 | 全盘 40 分钟 → **25 分钟以内**，且不用搬设备 |
| **理架 / 找书** | 回一体机查，或凭记忆 | 抬腕扫一下：书架位、状态、谁借的、几号还 | 一次查询从"30 秒 + 走一趟"变成 **3 秒** |
| **现场还书** | 攒一堆书搬回一体机逐本扫 | 同学还书时当场扫，还完立刻归架 | 省掉"搬运 + 排队"两个动作 |

> **设计判断**：这不是"降级"，而是把一个模糊的"学生自助"想法，换成一个**角色清晰、场景具体、能被验证**的工具。管理员每天都会盘点、理架、收书；但不是每天都需要在手表上借书。

#### 5.3.2 手表端功能清单（v0.3 按优先级重排）

| 优先级 | 屏 | 功能 | 说明 |
|---|---|---|---|
| **P0** | W2 | **扫码查书** | 扫书码 → 书名 / 状态 / 借阅人 / 应还日 / 所属书架。理架与答疑的基础动作 |
| **P0** | W3 | **现场还书** | 扫书即还，**不需要选人**（书上有借阅记录）。手表上最顺的一个动作 |
| **P0** | W4 | **移动盘点** | 接入进行中的盘点单，扫一本记一本；实时显示"已扫 / 应扫 / 缺失" |
| **P1** | W1 | 今日待办 | 今天到期 N 本、逾期 M 本；可按书架排序，用于巡架催还 |
| **P1** | W5 | 到期提醒推送 | **推给管理员**：「今天 5 本到期」，而不是推给学生 |
| **P2** | W6 | 扫码借书 | 扫书 → 从"最近 8 人 + 姓名筛选"里选人。**可选功能**，主路径仍是一体机 |
| **P2** | W7 | 我的借阅 | 管理员自己借的书（他也是一名学生） |
| **P3** | W8 | 续借 | 学生来找时现场操作；屏小，价值有限 |

**明确不做**：检索列表、书架浏览、图书详情长文、统计报表、成员管理、规则配置、任何删除类操作。

#### 5.3.3 三个新问题（替换 v0.2 的"三约束"）

**问题一：网络 —— 原来的死结基本解开了**

v0.2 最棘手的是"45 台 4G 手表够不着局域网"。现在只有 **1 台**，而且是**固定的、可由老师协助配置的**设备：

| 方案 | 可行性 | 成本 | 推荐度 |
|---|---|---|---|
| **连教室 WiFi，直连局域网** | 高（1 台设备，老师可协调） | 0 | ★★★★★ **首选** |
| 手表用 4G 直连 | 不可能（私有 IP 不可路由） | — | ✘ |
| 轻隧道（cloudflared / 花生壳） | 中 | 0 | ★★★ **备选** |
| 直接上云托管整站 | 中 | 150–250 元/年 | ★★ 违背 Q3 初衷 |

> **结论：优先让这 1 台手表连上教室 WiFi。** 这一步能省掉整个隧道方案、相应的公网暴露面和安全加固工作——是 v0.3 最大的简化。
>
> **如果 WiFi 因学校网络认证/白名单接入不了**，再启用隧道；此时暴露面只服务 1 台设备，风险远小于 45 台，但仍须遵守"只放行 `/api/watch/*`"的底线。

**问题二：权限 —— 这台手表丢了，等于一把能改账的钥匙**

这是本轮**风险反而上升**的地方。v0.2 的手表是学生只读终端，丢了影响有限；现在它绑的是图书管理员，**能做账务变更**（还书、盘点上报）。

| 措施 | 说明 |
|---|---|
| **设备锁** | 手表本身设 4 位锁屏 PIN；微应用启动再校验一次（双保险） |
| **短令牌** | `device_token` 有效期 **30 天**，到期需班主任重新授权 |
| **远程吊销** | 管理端一键吊销，服务端立即拒绝（校验 `status`，不等 token 过期） |
| **最小操作面** | 手表端**不允许**删除/注销副本、不允许处置盘点差异、不允许改规则——这些只能回一体机做 |
| **二次确认** | 还书与盘点上报均需点一次确认（不做"扫完自动提交"） |
| **审计可追溯** | 所有手表操作记 `device_id` + `client_op_id`，可按设备筛出全部动作 |
| **换届交接** | 图书管理员换届/毕业时，旧表解绑、新表绑定，2 分钟完成（Q20） |

**问题三：扫码 —— 仍然扫 QR 而非 Code128（此结论不变）**

米兔这类设备通常是百万像素级、泛焦摄像头，配 1.4 英寸左右取景屏（**具体参数以实机为准，S0 PoC 实测**）：

| 码制 | 手表识别成功率 | 原因 |
|---|---|---|
| Code128 一维码 | 中 | 要求条码在画面中**近似水平**，手持难保持；对焦不准时条纹糊成一片 |
| **QR 二维码（H 级纠错）** | **高** | 二维定位，任意角度可识别；H 级纠错容忍 30% 污损；对手抖与轻微失焦更宽容 |

**结论：标签同时印两种码。**
- **Code128** → 给扫码枪用（一体机端，识别率接近 100%、速度最快）
- **QR** → 给手表摄像头用（管理员移动操作）

标签尺寸 **50×25mm**（v0.1 为 40×20mm），左侧 QR、右侧 Code128、下方印书名与分类色条，**必须哑光**（亮面覆膜在日光灯下反光，QR 直接扫不出）。

**配套的体验细节**

| 问题 | 处理 |
|---|---|
| 扫错书 | 识别后**必须弹确认卡片**（书名 + 状态），点确认才提交 |
| 重复扫同一本 | 同一码 3 秒内不重复提交（前端防抖 + `client_op_id` 幂等） |
| 光线不足 | 取景框提示"请靠近一点/光线暗"；标签用哑光材质 |
| 网络慢 | 立即显示"处理中…"，超 3 秒提示"网络较慢"，避免反复点 |
| 失败看不懂 | 完整句子：「这本书不在借出记录里，可能已经还过了」 |
| 手表丢失/没电 | 回一体机操作，**系统不因手表不可用而不可用** |

#### 5.3.4 连带影响与补偿（v0.3 必读）

> 这一变更有一个必须说清的负面效应，不能含糊带过。

**问题**：v0.2 里，45 台学生手表是"到期提醒"唯一能触达孩子本人的通道。现在手表在管理员手上，**学生个人不再收到任何提醒**。提醒通道只剩：

1. 班级大屏（晨间 + 放学前各一次）
2. 纸质书签（借出时随书夹入，写到期日）

也就是说，"孩子在家想起要还书"这件事，系统**彻底无法干预**。这比 v0.2 又弱了一档（v0.2 至少还有学生手表）。

**补偿：从"推送提醒"改为"人主动催还"，而且可能更有效**

> **管理员可以拿着手表巡架、巡场，主动催还。**

| 原来的机制 | 现在的机制 |
|---|---|
| 系统推送 → 等学生看通知 | 管理员扫一下书架 → 知道谁的、超期几天 → 走到同学面前说"你这本超期了" |
| 依赖孩子自觉 | 依赖同伴提醒 |
| 转化率取决于孩子是否看手表 | 转化率取决于**有没有人当面说** |

对于这个年龄段，后者的实际效果通常远高于前者——孩子大概率不会主动翻通知，但一定会理会站在面前的同学。

**所以手表端的"今日待办 + 扫码查书"，实际承担的是"催还工具"的角色。** 这也是它比"学生端推送"更有价值的地方。

> **建议在 S8 试运行期专门验证这一条**：让管理员每天用 5 分钟巡架催还，记录逾期率变化。如果两周内逾期率没有下降，说明这个机制不成立，届时需要重新评估是否引入家长端（这会推翻 Q2 的一条结论）。

### 5.4 核心业务流程

#### 5.4.1 图书入库与上架

| 步骤 | 操作 | 系统行为 | 异常处理 |
|---|---|---|---|
| 1 | 扫描 ISBN（或手动输入书名） | 查询书目元数据，带出书名/作者/封面 | 查不到 → 手动填写，标记 `source=manual` |
| 2 | 选择分类、适读年级、标签 | 保存 book 记录 | — |
| 3 | 输入册数（如 3 册） | 批量生成 3 个副本，分配条码 | 条码冲突 → 自动续号 |
| 4 | 打印标签并粘贴 | 生成 PDF 标签页（含条码 + 书名 + 分类色） | 打印机故障 → 支持先入库后补打印 |
| 5 | 扫描每册条码确认上架 | 记录 `copy.status=available`、书架位置 | 漏扫 → 可在盘点时补 |

> 单本录入目标耗时：快速模式 **25–35 秒/本**（含贴标），完整模式 60–90 秒。
> **建库不要一次做完**——800 本完整录入需 13–20 小时，必然做不完。按 6.7.4 的三步策略推进。

#### 5.4.2 借书

| 步骤 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点击「借书」大按钮 | 进入借还台，弹出**全班头像网格** |
| 2 | **点头像选人**（Q2 定案，取消学生卡） | 显示大号姓名确认条 + 当前在借 n/3 + 是否有逾期；"最近借过的 8 人"置顶 |
| 3 | 扫书码 | 显示书名、副本状态 |
| 4 | — | 校验：副本 available？额度未满？逾期未达禁借阈值？ |
| 5 | — | 创建借阅单，`due_at = 服务端今日 + 14 天` |
| 6 | — | 界面反馈：**绿色大字 + 提示音**「借阅成功 ·《XX》· 11月2日前归还」 |

**校验失败时的提示必须是"人话"**：
- ❌ 不说 `COPY_STATUS_INVALID`
- ✅ 说「这本书已经被王小明借走了，11月1日归还」

**断网时**：本地入队，界面显示黄色「已记录（待同步）」，恢复网络后自动提交。此时仍允许继续借下一本。

> **点选身份的两个细节**：① 45 人头像一屏放不下，必须支持按学号排序 + 最近使用置顶 + 姓名首字筛选；② 点选后**必须有姓名确认条**，因为孩子很容易点错邻座同学。

#### 5.4.2b 还书（手表 · 图书管理员现场操作，v0.3 重写）

> v0.2 这里原本是"手表自助借书"。改为 1 台管理员手表后，手表做借书需要在 1.4 英寸屏上从 45 人里选人，体验不成立。**手表最适合的动作是还书**——因为还书根本不需要选人。

| 步骤 | 操作 | 系统行为 |
|---|---|---|
| 1 | 抬腕 → 点「还书」 | 直接进入扫码取景（**不选人**） |
| 2 | 扫书上的 **QR 码** | 本地解码，震动提示已识别 |
| 3 | — | 反查该副本 active 借阅单，弹出确认卡：书名 + 借阅人 + 是否逾期 |
| 4 | 点「确认归还」 | 提交；服务端结单，副本转 available |
| 5 | — | 绿底 + 震动：「已还 · 王小明 · 逾期 3 天」 |

**为什么还书最适合手表**：书的借阅记录里已经写着"谁借的"，所以还书**天然不需要身份选择**——这正好绕开"手表屏选不了人"这个死结。而且同学把书交回来是随机、分散发生的，能当场扫掉就不必攒到一体机。

**借书仍以一体机为主路径**（5.4.2）。手表端的借书列为 P2 可选功能：若实现，流程是"扫书 → 从最近 8 人 + 姓名筛选中选人 → 确认"，并明确标注为次选路径。

**手表不做离线队列**：断网时扫码可解码但提交失败，明确提示「没有网络，请到借还台操作」。孩子看不见同步状态，静默失败比直接报错更糟。

#### 5.4.3 还书（一体机 / 移动端）

| 步骤 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点击「还书」 | — |
| 2 | **只扫书码**（无需选人） | 反查该副本的 active 借阅单 |
| 3 | — | 结单：`status=returned`、`returned_at=服务端时间`、副本转 available |
| 4 | — | 若逾期：显示「逾期 3 天 · 请提醒王小明」；逾期记录进统计，不扣任何分数 |

**设计要点**：还书**不需要选人**。孩子来还书时经常说不清自己是谁，扫书就能定位到人。这是降低摩擦的关键取舍，也是还书比借书更快的原因。

**30 秒撤销**：还错了（比如把别人刚还的书又扫了一次）可在 30 秒内点"撤销"，恢复借阅单。

#### 5.4.4 续借

| 触发方 | 条件 | 结果 |
|---|---|---|
| 学生（手表 / 共用设备点选） | 未逾期 + 续借次数 < 1 | `due_at += 7 天`，`renew_count + 1` |
| 图书管理员（代操作） | 同上 | 同上，记录 `operator_id` |
| 已逾期 | — | 拒绝，提示"请先归还" |
| 已达上限 | — | 拒绝，提示"每本书只能续借 1 次" |

#### 5.4.5 逾期提醒（v0.3 通道再调整）

> v0.2 取消家长端后剩 3 条通道；v0.3 手表从学生转到管理员，**面向学生的推送通道归零**，只剩"在校可见"的两条，加上一条人工机制。

```
每日 07:30 定时任务
   ↓
扫描 loan 表：status=active 且 due_at 在 [now-1d, now+3d] 或逾期
   ↓
按规则生成 reminder 记录（dedup_key = loan_id + type，唯一索引防重）
   ↓
过滤：免打扰时段 → 顺延；已还 → 丢弃
   ↓
分通道投递（并发）
   ├─ 班级大屏（学生侧唯一可见通道，08:00 刷新今日应还榜 + 放学前再播一次）
   ├─ 纸质到期书签（零成本兜底，借出时随书夹入）
   └─ 管理员手表（工作提醒，非个人提醒）：「今天 5 本到期，3 本已逾期」→ 点开看名单
   ↓
【人工机制】管理员每日巡架 5 分钟，手持手表按书架顺序扫一遍，
             现场发现超期书 → 直接找到人催还
   ↓
记录 sent_at / status=failed，进入下次重试窗口
```

**v0.3 必须承认的局限**：学生本人**收不到任何推送**。"孩子在家想起要还书"这件事，系统彻底无法干预——比 v0.2 又弱一档。

**补偿机制的有效性判断**：把"推送等孩子看"换成"管理员走到面前说"。这个年龄段前者转化率低，后者往往更有效。因此手表端的「今日待办 + 扫码查书」实际上是**催还工具**，而不是"提醒功能的替代品"。

> **验证方式**：S8 试运行期设一个明确指标——管理员每天巡架 5 分钟，两周后比较逾期率。若无改善，说明该机制不成立，需要回头讨论是否重启家长端（会推翻 Q2 的一条结论）。

#### 5.4.6 库存盘点

| 阶段 | 操作 | 说明 |
|---|---|---|
| 建单 | 选择范围（全库/分类/书架） | 范围越小越快；建议日常只盘"本周借还过的书架" |
| 快照 | 系统写入应有清单 | 记录每册的预期状态与位置 |
| 扫描 | 逐册扫码 | 重复扫提示"已扫过"；不在清单内的书标为 `extra`（错架或未入库） |
| 看板 | 实时显示 已扫/应扫/缺失 | 进度条 + 缺失清单 |
| 结束 | 生成差异单 | 三分类：missing（应有未扫到）、misplaced（在其他位置扫到）、extra（系统无记录的实物） |
| 处置 | 班主任逐条确认 | 「在别处找到」→ 改书架；「确认丢失」→ 走 M3 丢失登记；「无异常」→ 归档 |

**耗时预估**：800 册全盘，单人扫码约 25–40 分钟；分书架抽盘每次 5–10 分钟。

### 5.5 三端数据同步机制

#### 5.5.1 同步拓扑

**星型结构，服务端为唯一中心。** 三端之间零直连，因此：

- 不存在"手表和手机的数据打架"
- 不存在"两台设备互相覆盖"
- 所有冲突都是「端 vs 服务端」的二元问题，可穷举、可裁决

#### 5.5.2 数据分级与新鲜度要求

| 数据类别 | 例子 | 一致性要求 | 同步方式 | 允许延迟 |
|---|---|---|---|---|
| **A 类：账务写** | 借出、归还、续借、丢失登记 | **强一致**（服务端裁决） | 同步请求；离线时入队，联网立即重放 | 0 秒（在线时） |
| **B 类：主数据写** | 书目编辑、分类调整、成员变更 | 最终一致 | 同步请求 + 失败重试 | ≤ 5 秒 |
| **C 类：只读查询** | 检索、书架、统计 | 允许轻微陈旧 | 请求即取 + 短缓存（30 秒） | ≤ 30 秒 |
| **D 类：推送通知** | 到期/逾期提醒 | 尽力送达 | 定时任务 + 多通道重试 | ≤ 5 分钟 |
| **E 类：手表数据** | 今日待办、提醒卡片、盘点进度 | 最终一致 | 唤醒时拉取 + 推送触发 | ≤ 5 分钟 |
| **F 类：手表写**（v0.3 修订） | 现场还书、盘点上报、借书（可选） | **强一致**（与 A 类同源） | 同步请求，**不排队、不缓存** | 0 秒 |

#### 5.5.3 各端同步实现

**Web 管理端**
- 常驻页面，操作即请求
- 离线队列：`IndexedDB`（Dexie）存 `pending_ops`，每条含 `client_op_id`（UUID）、`device_id`、`device_seq`（设备内单调递增）、`client_ts`、`payload`
- 恢复网络：按 `device_seq` 顺序串行重放，逐条等待服务端确认
- 页面顶部常驻同步状态条：`已同步 / 待同步 3 条 / 同步失败（点击处理）`

**移动端（PWA）**
- 同上，队列逻辑复用
- 额外具备"扫码即提交"，一次操作一个请求，不做批量

**手表端（v0.3 重写）**
- **无本地数据库**，只有内存缓存与一个"待确认操作"的临时态
- 唤醒 / 收到推送时拉取一次聚合接口（今日待办 + 盘点进度 + 提醒）
- **手表不参与离线队列**：还书、盘点上报属于 F 类强一致写，网络不通就明确报错并提示"请到借还台操作"
  - 原因一：管理员的设备在移动中，网络时断时续，静默排队会造成"我以为还了，其实没还"
  - 原因二：随身设备的操作必须当场看到结果，否则管理员会重复操作
- 断网时展示缓存数据 + "数据截至 HH:mm"角标
- 所有写入必须带 `client_op_id`，防止网络慢时反复点击造成重复还书
- **盘点场景的特殊处理**：盘点数据量大、可能长时间在无网区域移动，因此允许"本地暂存已扫记录"，但必须在页面显著位置显示「未上报 N 本」角标，回到有网处立即批量提交。这是唯一允许的"准离线"场景

#### 5.5.4 幂等与去重

每一条写请求携带 `client_op_id`（UUID v4），服务端 `op_log.client_op_id` 建唯一索引：

- 首次提交 → 执行 → 记录结果
- 重复提交（网络重试、用户连点）→ 命中唯一索引 → **直接返回首次结果**，不重复执行

这条机制解决三类问题：用户连点、网络超时重试、离线队列重复重放。

### 5.6 冲突处理原则

#### 5.6.1 三条总原则

1. **宁可阻断，不可错账。** 借还类账务冲突一律不自动合并，失败方明确报错并由人处理。
2. **服务端时间是唯一业务时间。** 客户端时钟不可信（孩子的手表时间可能差几小时），业务时间戳全部由服务端生成。
3. **描述性数据可覆盖，账务数据不可覆盖。** 书名写错了可以后写覆盖前写；借阅记录永远只追加、不覆盖。

#### 5.6.2 冲突场景与裁决规则

| # | 冲突场景 | 检测方式 | 裁决规则 | 用户看到什么 |
|---|---|---|---|---|
| C1 | 两台设备（如两台平板）同时借出同一册 | 副本 `version` 乐观锁 CAS 更新失败 | **先提交者胜**，后到者失败 | 「这本书刚被借走了，请重新扫描」 |
| C2 | 网络超时导致重复提交 | `client_op_id` 唯一索引 | 幂等：返回首次结果 | 无感知 |
| C3 | 离线期间同一册"先还后借" | 按 `device_seq` 顺序重放 + 状态校验 | 按序执行；若第二步状态非法则整条挂起 | 进入「待核对」队列，班主任处理 |
| C4 | 还书时该书已被标记丢失 | 副本状态 ≠ borrowed | 拒绝自动结单，转异常队列 | 「该书已被登记为丢失，请联系班主任」 |
| C5 | 两人同时点续借 | `loan.version` 乐观锁 | 先到先得，第二次拒绝 | 「已续借过」或「该书已被预约」 |
| C6 | 书目信息被两端同时编辑 | `updated_at` 比较 | **LWW（后写覆盖）**，按服务端接收时间 | 静默处理，审计日志留痕，可回溯 |
| C7 | 同一个学生在两台设备上被同时借书，超出额度 | 事务内 `SELECT ... FOR UPDATE`（SQLite 用立即事务） | 严格串行，第二次校验失败 | 「已达 3 本上限，请先归还一本」 |
| C8 | 客户端时间错误导致 due_at 异常 | 服务端强制重算 | 忽略客户端时间 | 无感知 |
| C9 | 学生已离班但仍有在借 | 离班前置校验 | 拒绝离班，提示"尚有 N 本未还" | 明确提示 |
| C10 | 盘点期间有人借书 | 盘点快照为"预期值"，允许实际变化 | 盘点结果标注"盘点期间发生借还 N 笔"，不算差异 | 差异单中单列说明 |
| **C11** | 管理员用手表还书，同时另一人在一体机上对同一册还书（v0.3 修订） | 借阅单 `status` 已非 active | 第二次操作幂等返回"已归还"，不报错、不重复结单 | 「这本书已经还过了」（温和提示，不当作错误） |
| **C12** | **这台手表丢失后被他人使用**（v0.3 风险升级） | `device_token` 有效性 + 锁屏 PIN + 远程吊销 | 吊销后立即拒绝所有请求；未吊销期间的操作只能靠审计追溯。**系统无法识别"是不是本人在用表"** | 手表端提示"设备已停用，请联系老师" |
| **C13** | 手表扫到了**别的班 / 已注销**的书的码 | 条码前缀 + 副本状态校验 | 拒绝，提示"这本书不是我们班的"／"这本书已经不在了" | 明确文案，不显示技术错误 |
| **C14** | 管理员连续扫同一本（手抖重复扫） | 前端 3 秒防抖 + `client_op_id` 幂等 + 服务端识别"已归还" | 幂等返回首次结果，不重复提示成功 | 「这本刚才已经还了」 |
| **C15** | 手表端盘点上报与一体机盘点同时进行（v0.3 新增） | 同一 `session_id` 下的 `copy_id` 唯一索引 | 先到先记；后者返回"已扫过"。两者共用同一盘点单，进度实时合并 | 手表显示"这本书刚才已经扫过了" |
| **C16** | 手表本地暂存了盘点记录，但一直没回到有网环境（v0.3 新增） | 页面常驻「未上报 N 本」角标 | 不自动丢弃；关闭页面前二次确认；班主任端可看到"某设备有未上报记录" | 明确提示，不静默丢失 |

#### 5.6.3 异常队列（人工兜底）

无法自动裁决的操作进入「待核对」队列，仅在班主任端可见：

- 每条显示：谁、什么操作、原始请求、冲突原因、建议处置
- 处置选项：**采纳**（强制应用）/ **丢弃**（放弃该操作）/ **修正后应用**
- 所有处置写入审计日志

**这个队列的存在，是"不自动合并"原则能够落地的前提**——冲突不能被悄悄吞掉，必须有人看见。

### 6.3 推荐方案

> **推荐方案 B（PWA + 自托管 + SQLite），按 Q3 定案采用「教室本地部署」。**
>
> 在三个候选中，B 是唯一能同时满足四项硬约束的方案：① 零成本；② 断网仍可操作；③ 手表需要公网入口时，能**只放行一小段白名单路径**，而不是把整站和数据库摆到公网；④ 一套前端代码同时喂给 Web、手机、手表三种视口。

#### 6.3.1 具体技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | **Vue 3 + Vite + TypeScript** | 生态成熟、体积小、上手快；单人也易维护 |
| UI / 样式 | **TailwindCSS + 自研大按钮组件** | 需要为儿童定制大字号、高对比度、色块分类，通用组件库反而碍事 |
| 状态与本地存储 | **Pinia + Dexie（IndexedDB）** | Dexie 处理离线队列非常顺手 |
| 扫码 | **扫码枪（HID 键盘模拟）+ html5-qrcode / zxing-wasm** | 扫码枪为主（零延迟），摄像头为备 |
| 图表 | **ECharts** | 统计页需要，体积可接受 |
| 后端 | **Node 20 + Fastify + Zod** | 比 NestJS 轻，比 Express 现代；Zod 做参数校验，减少样板代码 |
| 数据库 | **SQLite（WAL 模式）+ Drizzle ORM** | 单文件、零运维、备份=复制文件；这个数据量 SQLite 完全够用，写 QPS 可达数百 |
| 定时任务 | **node-cron**（进程内） | 只有一个每日任务，不需要独立调度系统 |
| 备份 | **每日 `sqlite3 .backup` + 保留 30 天 + 每周导出 xlsx** | 单文件备份极简单，恢复=替换文件 |
| 部署 | **Windows 服务（NSSM 包装）+ 单目录发行包**；Docker 为可选项 | 本地部署下 Docker Desktop 常与教室电脑的 Hyper-V/驱动冲突，直接用 Node 服务 + 服务包装更稳、更好交接 |
| 推送 | **米兔推送通道 + 班级大屏 + 纸质书签** | Q2 取消家长端后，微信推送已无必要；手表推送是唯一"跟着人走"的通道 |
| **公网出口** | **默认不需要**；仅在手表无法接入教室 WiFi 时启用 **cloudflared** | v0.3 关键简化：1 台设备走局域网即可，公网暴露面归零。隧道降为备选，且只放行 `/api/watch/*` |
| **手表容器** | **米兔微应用（H5 视口）** | 复用同一套 Vue 前端，只做 320×320 视口适配；只装 1 台，**可侧载安装**，无需走应用市场上架（前提是 Q15 确认可侧载） |

#### 6.3.2 两种部署形态

**形态 B-：教室本地部署（Q3 定案，本方案采用）**

- 载体：教室一体机或旧笔记本（Win10/11 / 4G 内存 / 128G 硬盘）
- 访问：局域网 `http://<固定IP或主机名>:8080`
- 成本：**0 元/年**
- 优点：数据在自己手里、断网可用、零月费、零备案、不受任何平台规则影响

**必须做的四件运维小事（缺一件就会出事）**

| 事项 | 做法 | 不做的后果 |
|---|---|---|
| **固定地址** | 路由器做 DHCP 静态绑定，或主机设静态 IP | IP 一变，大屏和所有平板立即连不上，且没人知道为什么 |
| **开机自启** | 用 NSSM 注册为 Windows 服务 | 停电或意外重启后，系统不会自己起来 |
| **禁止睡眠** | 电源选项设为"从不睡眠/从不关闭硬盘" | 夜里休眠，第二天全教室连不上 |
| **异地备份** | 备份文件写入 OneDrive/坚果云**同步目录** | **硬盘坏了数据全没**——本机备份等于没备份 |

> ⚠️ 最后一条是本地部署最大的认知陷阱：很多人以为"每天备份到 D 盘"就安全，但硬盘故障时 D 盘和数据库一起消失。**备份必须离开这台机器**，这是唯一有效的约束。

> ⚠️ **另一个必须提前说明的技术细节**：Service Worker（PWA 的离线缓存）**只在 HTTPS 或 localhost 下可用**，局域网 IP 的 http 访问无法注册 SW。
> **应对**：本地形态**不依赖 SW**，离线能力用「页面常驻 + IndexedDB 队列」实现——这已满足"断网时操作不丢"的核心诉求。完整 PWA 离线打开能力，留到上云（HTTPS）后再启用。这个取舍必须写进方案，否则会在实现阶段踩坑。

**形态 B+：云托管（本期不采用，保留为备选）**

- 触发条件：后期要求"学生在家也能查"、"同年级多班共用"、或本地主机频繁故障
- 做法：把同一个发行包搬上 1 核 2G 轻量云（约 100–150 元/年）+ 域名（10–30 元/年）+ 备案（免费，约 20 天）
- 成本：**约 150–250 元/年**
- 迁移成本：**拷 `library.db` 一个文件 + 改一个环境变量，约 10 分钟**

> **关键设计要求**：不在代码里硬编码"本地"假设（如写死 `localhost`、依赖 Windows 路径），所有外部地址走配置。这样 Q3 万一变化，不会返工。这也是为什么选 SQLite 而不是需要独立服务的数据库——数据就是一个文件，搬家极其简单。

**建议路径**：先按 B- 跑一个学期，验证流程真的被用起来，再决定是否花钱上云。**不要一开始就为"可能没人用"的功能付费。**

#### 6.3.3 推送通道选型

| 通道 | 成本 | 到达场景 | 依赖 | 定位（v0.2 重排） |
|---|---|---|---|---|
| **手表推送** | 依赖厂商通道，通常 0 元 | 学生随身，**校外也能收到** | 米兔推送开放能力 | **主通道**（唯一能触达家庭的通道） |
| **班级一体机大屏** | 0 | 在校时 100% | 无 | **主通道**（每日 08:00 今日应还榜 + 放学前提醒） |
| **纸质到期书签** | ≈0.02 元/张 | 夹在书里，回家可见 | 无 | **实体兜底**（借出时随书夹入，写到期日 + 书名） |
| 短信 | 0.04–0.05 元/条 | 手机 | 需采集家长手机号（**Q2 已取消，不建议启用**） | 不采用 |

> **触达路径的诚实评估**：取消家长端后，系统对"孩子在家里忘带书"这件事**没有任何远程干预手段**。三条通道全部发生在孩子身边——手表、教室大屏、夹在书里的书签。这是一个必须在评审时明确接受的产品局限。
>
> 如果试点期逾期率明显偏高（例如 > 30%），说明"没有家庭触达"是硬伤，届时再评估是否引入家长端（成本与合规代价见 Q2 的原始权衡）。

> **推送是"尽力而为"，不是"保证送达"。** 系统的可靠性建立在"书还在教室里"这个物理事实上，而不是推送成功率上。

### 6.4 硬件与耗材清单

| 项目 | 规格建议 | 单价 | 数量 | 小计 | 是否必需 |
|---|---|---|---|---|---|
| USB 扫码枪 | **二维影像式**（可同时读 QR 与 Code128），HID 键盘模拟，免驱 | 120–200 元 | 1 | 约 150 元 | **强烈建议** |
| 不干胶标签纸（**哑光**） | A4，50×25mm 双码排版，每张约 24 枚 | 约 30 元/包 | 1 包 | 30 元 | 必需 |
| 到期书签卡纸 | A4 卡纸，每张裁 8 条 | 约 15 元/包 | 1 包 | 15 元 | 建议 |
| 标签打印机（可选） | 热敏 203dpi，支持 50×25mm | 约 200 元 | 1 | 200 元 | 可选，普通激光打印机可替代 |
| 旧手机/平板（可选） | 摄像头 ≥ 200 万像素，作备用扫码器 | 0 | 1 | 0 | 可选 |

**一次性投入：约 200–250 元；每学期耗材：约 50 元。**

> **v0.2 变更**：取消学生卡（Q2 改为点选身份，省 25–90 元），但扫码枪升级为二维影像式、标签从 40×20mm 放大到 50×25mm 并印双码（为了手表能扫 QR），成本基本持平。

> ⚠️ **标签材质必须是哑光**。亮面/覆膜标签在教室日光灯下会形成镜面反射，二维码直接扫不出来——这是纸质标签最常见的翻车点，且很难事后补救（只能整批重印）。

> **关于扫码枪为什么值得买**：一支 150 元的二维影像枪，识别耗时 < 100ms、免对焦、不怕反光、不怕孩子手抖，比手机摄像头快 5–10 倍且几乎不会失败。这是整个系统体验的**最大单点收益**，比任何软件优化都划算。

### 6.5 小学生易用性设计要点

| 场景 | 常见做法（不适合） | 本方案做法 |
|---|---|---|
| 登录 | 用户名 + 密码 | **零登录**：管理员点头像选人；学生用手表即身份 |
| 找书 | 搜索框 + 关键词 | **分类色块 + 封面墙**，搜索为辅助 |
| 打字 | 拼音全拼 | 支持**拼音首字母**（`xlsw` → 夏洛的网） |
| 借书 | 多步表单 | 管理端：点人 + 扫书；手表：**扫书 + 点确认**（只需 1 次扫码） |
| 反馈 | 文字提示"操作成功" | **大字 + 颜色 + 提示音**，显示"11月2日前还" |
| 错误提示 | 错误码 | 人话，含具体人名与日期 |
| 按钮尺寸 | 32–40px | **≥ 64px**，主操作占屏幕 1/3 |
| 颜色语义 | 蓝色主色 | **绿色=借、蓝色=还、红色=逾期、黄色=待同步** |
| 误操作 | 二次确认弹窗 | **30 秒撤销**（比弹窗更有效，且不打断流程） |
| 管理员界面 | 功能齐全的侧边栏 | 默认只有**两个大按钮**：「借书」「还书」，其余收进"更多" |

**低年级特别处理（若 Q10 回答为一年级）**：
- 分类图标用图形而非文字
- 书名旁显示"适读年级"色带
- 支持语音输入（Web Speech API，Chrome 可用）
- 借还成功可播放语音播报

**手表端的专项易用性（v0.3：使用者是学生管理员，不是幼儿，规则可略放宽）**

| 问题 | 手表上的做法 |
|---|---|
| 取景框太小对不准 | 全屏取景 + 中央大方形定位框 + 「把书上的方块对准框里」；识别成功后**冻结画面 300ms**，让人确认"扫到了" |
| 屏幕小看不全 | 每屏**只放一件事**；查书结果用"三行式"（书名 / 状态 / 谁借的），不堆字段 |
| 触摸不准 | 可点区域 ≥ 44×44px（占屏宽 1/3 以上），按钮间距 ≥ 8px |
| 看不出成功与否 | **震动 + 声音 + 满屏纯色**三重反馈（绿=成功/红=失败），余光也能看见 |
| 查书与还书混淆 | **拆成两条独立入口**：查书只读不改；还书才走确认提交。避免"只想查一下，结果还了" |
| 盘点时频繁打断 | 盘点模式**连扫不打断**（只在异常时震动提醒），否则几百本书根本扫不完 |
| 误触提交 | 还书需点一次确认；**盘点为一键连扫，但可随时暂停**——两种场景的取舍不同 |

### 6.6 明确不推荐的做法

| 做法 | 为什么不做 |
|---|---|
| 微服务 / 容器编排（K8s） | 45 个用户，运维成本远超收益 |
| 引入 Redis / 消息队列 | 单机 SQLite + 进程内定时任务足够 |
| 自建推送服务 | 维护成本高，第三方免费额度足够 |
| 每个学生一个账号密码 | 孩子记不住、老师管不过来，必然退化为"共用账号" |
| 人脸识别借书 | 合规风险高、成本高、识别率不稳定 |
| 区块链存证 | 完全无必要 |
| 一开始就做多租户 SaaS | 过度设计，先跑通一个班 |
| 做原生 App（iOS/Android） | 需双端开发 + 上架审核，收益为零 |

### 6.7 ISBN 元数据方案与「分批建库」策略（v0.2 新增）

> Q4 定案为"没有书单、靠扫 ISBN 自动带出"，这一节解决由此产生的两个真问题：**数据源从哪来**、**800 本书怎么录得完**。

#### 6.7.1 现实前提：没有一个稳定免费的中文 ISBN 接口

| 数据源 | 中文童书覆盖 | 成本 | 稳定性 | 说明 |
|---|---|---|---|---|
| Google Books API | 中 | 0（有配额） | 中 | 国内访问可能需代理，Q19 需实测连通性 |
| 豆瓣图书 | 高 | 0 | **低** | 无公开 API，网页接口有风控，随时失效。**不可作为唯一源** |
| Open Library | 很低 | 0 | 中 | 中文童书基本查不到 |
| 国家图书馆联机目录 | 高 | 0 | 中 | 只有网页，字段不全，需抓取 |
| 京东/当当开放平台 | 高 | 需资质 | 高 | 个人难以申请 |
| **自建 `isbn_cache`** | 随使用积累 | 0 | **最高** | 查过一次就永久命中，越用越准 |

**结论：不要指望"一个接口搞定"，要设计降级链。**

#### 6.7.2 三级查询 + 本地缓存（降级链）

```
扫 ISBN
  ↓
① 查本地 isbn_cache ──命中──► 立即返回（0 延迟，永不失败）
  ↓ 未命中
② 主数据源（可配置，默认 Google Books）──超时 3 秒──► 成功则写入缓存
  ↓ 失败
③ 备数据源（可配置第二个）──超时 3 秒──► 成功则写入缓存
  ↓ 全部失败
④ 手动录入（ISBN 已预填，书名必填，其余可空）
```

**关键设计：每次成功查询都写回 `isbn_cache`。** 童书重复率极高（同年级、往届、兄弟班），缓存积累起来后，第二个班建库的命中率可能超过 60%，外部依赖会随时间自然衰减。

#### 6.7.3 无 ISBN / 扫不出的书怎么处理

小学图书角必然存在大量这类书：往届留下的旧书、套装书、盗版书、条码被贴纸盖住的、条码磨花的。

**必须支持「内部码」机制，否则建库会在第一批旧书上卡死：**

| 项 | 做法 |
|---|---|
| 条码 | 生成内部码，前缀 `X` 与正常 ISBN 区分（如 `X030100456`） |
| 元数据 | 书名手动输入（必填）、分类必选，作者/封面留空 |
| 系统地位 | 与正常书**完全等价**，可正常借还、盘点、统计 |
| 展示 | 详情页标注「内部编码」，无封面时用色块 + 首字占位 |

#### 6.7.4 分批建库策略（本节最重要）

800 本 × 完整录入 60–90 秒 ≈ **13–20 小时**。没有人会干完这个活，**任何"先建全库再上线"的计划都会失败**。正确做法是分三步：

| 阶段 | 做什么 | 数量 | 耗时 | 目的 |
|---|---|---|---|---|
| **① 冷启动** | 只录最热门/最新的书，用快速模式 | 100–150 本 | 1.5–2.5 小时（分 2–3 次完成） | **当天就能开始借书**，先让系统活起来 |
| **② 借还即录** | 借书时若扫到的码系统不认，现场建档 | 按需增长 | 每次 30 秒，分散在借还过程中 | 借得越多的书，越早进库——正好是需求最高的书 |
| **③ 盘点补齐** | 全盘时把剩余未入库的一次性扫完 | 剩下的 | 40–60 分钟 | 一次性收尾，顺便完成首次盘点 |

**两种录入模式**

| 模式 | 采集字段 | 耗时 | 适用场景 |
|---|---|---|---|
| **快速模式** | ISBN + 书名（自动带出）+ 分类（默认值可改） | **25–35 秒/本** | 冷启动、借还即录 |
| **完整模式** | 再加作者/出版社/封面/简介/适读年级/标签 | 60–90 秒/本 | 后续批量补全，不阻塞收付 |

> 这个策略的价值不只是省时间，更重要的是**把"建库"这件事从一个必须一次性完成的门槛，变成可以随使用逐步积累的过程**。否则项目会卡在"书还没录完，所以还不能用"的死循环里。

#### 6.7.5 分类的自动建议（规则，不是 AI）

用关键词规则表，命中即预填，管理员一键确认或改：

| 关键词命中 | 建议分类 |
|---|---|
| 注音 / 拼音 / 一年级 / 大字 | 低年级读物 |
| 绘本 / 图画书 / 无字书 | 绘本 |
| 十万个为什么 / 科学 / 百科 / 恐龙 | 科普 |
| 历史 / 上下五千年 / 名人 / 传记 | 历史 |
| 童话 / 寓言 / 安徒生 / 格林 | 童话 |
| 其余 | 文学（默认） |

> **不要用大模型做分类**：要联网、不稳定、出错还没法解释，而规则表在 6 个分类的粒度上准确率已经足够。

### 7.2 实体字段表

#### class（班级）

| id | INTEGER PK | 主键 |

| created_at | DATETIME | 创建时间 |

#### user（成员）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 主键 |
| class_id | INTEGER FK | 所属班级 |
| name | TEXT | 姓名 |
| student_no | TEXT | 学号（班内唯一） |
| role | TEXT | `student` / `librarian` / `teacher` |
| avatar_url | TEXT | 头像（可选，用色块+首字替代） |
| pin_hash | TEXT | 4 位 PIN 的 bcrypt 哈希（仅 librarian / teacher 需要） |
| status | TEXT | `active` / `left`（离班，保留历史） |

> **v0.2 变更**：删除 `card_code` 与 `short_code`。Q2 改为"共用设备点选身份"后，学生不再需要任何可扫描/可输入的凭证。学生身份**只存在于内存中的临时会话**，不落库。管理员（图书管理员 / 班主任）仍用 4 位 PIN 登录，因为他们的操作需要留痕与追责。

> **敏感信息最小化**：主表**不存**家长手机号、身份证、住址。Q2 取消家长端后，**连 `parent_contact` 表也不需要了**——这是本版在合规上的一大简化。

#### watch_device（手表设备绑定，v0.3 加严）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 主键 |
| user_id | INTEGER FK → user | 绑定人（**必须 role = librarian 或 teacher**；1 人 1 台，换表需先解绑） |
| device_token_hash | TEXT UNIQUE | 令牌哈希（**不存明文**） |
| device_name | TEXT | 设备标识，如"米兔 6C" |
| bound_at | DATETIME | 绑定时间 |
| expires_at | DATETIME | **令牌到期时间（默认 30 天）**，到期需班主任重新授权 |
| pin_hash | TEXT | 手表端 4 位 PIN 的 bcrypt 哈希（**第二道锁**） |
| bound_by | INTEGER FK → user | 操作人（班主任） |
| status | TEXT | `active` / `revoked` / `lost` / `expired` |
| last_seen_at | DATETIME | 最近一次请求时间（用于排查"手表离线"） |

> 绑定流程：班主任在管理端为指定图书管理员生成 6 位**一次性绑定码**（5 分钟有效）→ 管理员在手表微应用输入 → 服务端校验后签发 `device_token` 并落库哈希。**首次绑定后需设置 4 位 PIN。**

> **安全要求（v0.3 加严）**：
> ① 手表请求**必须**由 `device_token` 反查 `user_id`（唯一例外是 `borrow` 接口，它显式携带目标学生 `user_id`，服务端需额外校验该学生属于本班且 active）；
> ② 被吊销/过期的设备**立即拒绝**，不等 token 自然过期；
> ③ `user_id` 绑定的用户若被改为 `student` 角色或置为离班，设备自动失效——防止权限降级后仍持有管理员能力。

#### watch_op_log（手表操作流水，v0.3 新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 主键 |
| device_id | INTEGER FK → watch_device | 设备 |
| action | TEXT | `lookup` / `return` / `inventory_scan` / `borrow` |
| target_barcode | TEXT | 操作对象条码 |
| client_op_id | TEXT | 幂等键 |
| result | TEXT | `ok` / `rejected:原因` |

### 7.3 关键设计决策说明

| 决策 | 内容 | 理由 |
|---|---|---|
| **D1** | **书目（book）与副本（copy）分离** | ① 同一本书 5 册，若只有一条记录则无法知道"还剩几本在架"；② 盘点必须逐册核对物理实体；③ 借阅单必须指向"某一册"而非"某种书"。这是一切账目正确性的地基 |
| **D2** | **逾期不落状态字段** | 逾期是时间函数，落库必然随时间失效。派生计算 + 冗余标记（仅供筛选）是唯一正确做法 |
| **D3** | **副本状态用乐观锁（version）** | 借还是并发敏感操作，SQLite 的写串行特性 + 应用层 CAS 足以保证一致，无需悲观锁 |
| **D4** | **借阅单只追加不覆盖** | 账目一旦发生就是历史事实；撤销不是删除记录，而是追加一条反向流水 |
| **D5** | **`client_op_id` 唯一索引** | 用数据库约束实现幂等，比应用层判断更可靠 |
| **D6** | **成员只有"离班"没有"删除"** | 历史借阅必须可追溯，删除用户会造成账目悬空 |
| **D7** | **分类不套用中图法** | 22 个大类对小学生无意义；6–8 个可视化分类足够 |
| **D8** | **标签同时印 Code128 与 QR**（v0.3 修订） | 两种码服务两种设备：Code128 给扫码枪（一体机端，快、准）；QR 给米兔手表摄像头（二维定位，不怕手抖与失焦，管理员移动操作时用）。单一码制必然牺牲一端体验 |
| **D9** | **手表身份用 `device_token`，除借书外不接受客户端传 `user_id`**（v0.3 加严） | 手表能改账，令牌即权限。除 `borrow` 这一特例外，身份一律服务端反查；`borrow` 携带的 `user_id` 也必须校验"本班 + active" |
| **D10** | **ISBN 元数据独立成缓存表，不直接写进 book**（v0.2 新增） | 缓存可跨班、跨届复用；`book` 只存"这个班实际拥有的书"。两者混在一起会导致缓存被班级数据污染，换班时无法复用 |

### 7.4 数据同步方式（分层说明）

| 层次 | 机制 | 说明 |
|---|---|---|
| **端 ↔ 服务端** | REST + 离线队列 + 幂等键 | 见 5.5、5.6 |
| **服务端内部** | 单库单事务 | 借还操作在单个 SQLite 事务内完成（校验 + 写 loan + 改 copy.status），天然原子 |
| **备份** | 每日 02:00 `sqlite3 .backup` → 保留 30 天；**备份文件写入 OneDrive/坚果云同步目录（异地）** | `.backup` 是热备份，不锁库；恢复=替换文件，< 3 分钟。**异地是硬要求**：本地部署下"备份到本机 D 盘"等于没备份 |
| **导出/迁移** | 全实体导出 xlsx + 全量 JSON 快照 | 保证"退出不锁定"，任何时刻可带走全部数据 |
| **多端一致性** | 无多主复制，无需 CRDT / 双向同步 | 星型拓扑的天然优势 |
| **手表通道** | 教室 WiFi 直连（首选）；仅在接入受限时启用隧道 + 路径白名单 | 手表端无本地数据库，天然无同步冲突 |

| T-U05 | 盘点模式 | 顶部进度"已扫 128 / 应扫 300"；中间最近扫到的书名 | 连续扫，无需逐条确认 | 自动连扫，**不做每次确认**（否则效率太低） |
| T-U06 | 今日待办 | 到期 N 本 / 逾期 M 本；列表按书架排序 | 上下滑，点击看详情 | 便于规划巡架路线 |
| T-U07 | 结果反馈 | 满屏纯色（绿/红）+ 一句话 | 2 秒自动返回 | 震动 + 提示音，余光可见 |
| T-U08 | 设备绑定 | 6 位数字输入 | 数字键盘 | 仅首次，班主任指导完成 |

**视口规格**：按 **320×320 逻辑像素**设计，等比适配 240×240 与 360×360；安全区留 12px；**不支持横屏**。

**与 v0.2 的关键差异**：
- 删掉"我的借阅"（不再是学生个人视角），换成「今日待办」
- 借还确认屏拆成「查书结果」+「还书确认」两屏，因为**查书是最高频动作**，它不该被绑定在借还流程里
- 盘点屏改为**连扫模式**——盘点时一次要扫几百本，每本都弹确认会让这个功能彻底没法用

**实现策略（依赖 Q15 结论）**：
- 若为 **H5 容器** → 复用同一套 Vue 前端，走 `/watch` 路由 + 独立 CSS 变量，**不重写业务逻辑**
- 若为**私有框架** → 只重写这 8 个屏的 UI 层，业务逻辑仍复用后端 API

> 这也是把"手表端"设计成"调用固定 5 个接口"的原因：无论前端用什么技术实现，后端契约不变。

**手表端明确不做**：检索列表、书架浏览、图书详情长文、统计、成员管理、规则配置、任何删除/注销/差异处置操作。

**手表端（v0.3 重写：5 个接口，服务于管理员的移动工作）**

> v0.3 前提变化：手表是**管理员设备**，主要做"查、还、盘"，不做"借"。接口全部在 `/api/watch/*` 前缀下——默认走局域网；若启用隧道，这一组路径就是唯一的公网暴露面，便于做白名单。

| 方法 | 路径 | 用途 | 说明 |
|---|---|---|---|
| GET | `/api/watch/summary` | 一次返回：今日待办（到期 N / 逾期 M）+ 进行中的盘点进度 + 最近提醒 | **单接口聚合**，减少请求次数与耗电 |
| GET | `/api/watch/book/:barcode` | **扫码查书**：书名、状态、借阅人、应还日、书架位 | P0。理架与答疑的基础动作 |
| POST | `/api/watch/return` | **现场还书**（扫书即还，无需选人） | P0。身份来自 `device_token` |
| POST | `/api/watch/inventory/scan` | **盘点上报**一册 | P0。可批量提交暂存记录 |
| POST | `/api/watch/borrow` | 借书（**可选，P2**） | 需带 `user_id`（由管理员在屏上选择），服务端校验该用户属于本班 |

> 隧道层配置要求（**仅在启用隧道时**）：只放行 `/api/watch/*`；其余路径返回 404；每设备限流 30 req/min；强制 HTTPS。

**关键约束（写在契约里，实现时必须遵守）**

| 约束 | 原因 |
|---|---|
| 除 `borrow` 外，手表请求**不得**携带 `user_id` | 身份一律由 `device_token` 反查，否则改参数即可冒用 |
| `borrow` 携带的 `user_id` 必须校验"属于本班且状态为 active" | 这是唯一允许传 user_id 的接口，必须单独加固 |
| 手表端**不做**通用离线队列 | 管理员在移动中，静默排队会导致"以为还了其实没还" |
| **盘点上报是唯一例外**：允许本地暂存 + 显式"未上报 N 本"角标 | 盘点时可能长时间处于无网区，必须允许暂存，但**必须让人看见** |
| 所有写操作必须带 `client_op_id` | 网络慢时反复点击必须幂等 |
| 手表接口响应体 ≤ 2KB | 屏幕小、流量敏感，禁止返回整本书详情 |

## 9. 非功能性要求

### 9.1 性能与容量

| 指标 | 目标 | 说明 |
|---|---|---|
| 容量 | 800 副本 / 45 用户 / 5 年流水约 3 万条 | SQLite 轻松承载，单表百万级才开始需要优化 |
| 响应时间 | 局域网 P95 < 100ms；云端 P95 < 300ms | 借还操作必须在 200ms 内出结果 |
| 扫码到反馈 | ≤ 500ms（含声音与界面） | 超过 1 秒孩子会重复扫 |
| 并发 | 峰值 5 并发写 | 单机足够，无需连接池调优 |
| 启动时间 | < 3 秒 | 一体机开机即用 |

### 9.2 安全与隐私

| 项 | 措施 |
|---|---|
| 传输 | 云端/隧道强制 HTTPS；纯局域网访问风险可控（但仍建议后续补 HTTPS） |
| 认证 | 管理端 JWT 7 天；管理员 PIN 用 bcrypt；**手表端 `device_token` 存哈希、可吊销、单设备单用户** |
| **公网暴露面** | **默认不暴露公网**（手表走局域网）；仅在启用隧道时放行 `/api/watch/*`，上线前实测"访问 `/api/books` 返回 404"；隧道域名不在班级群传播 |
| **手表设备安全（v0.3）** | 手表锁屏 PIN + 应用 4 位 PIN 双重锁；`device_token` 30 天到期；远程吊销立即生效；手表端禁用删除/注销/差异处置；全部动作记 `watch_op_log` |
| **手表接口滥用防护** | 每设备 30 req/min 限流；连续失败 5 次锁定 10 分钟；请求体大小上限 4KB |
| 越权防护 | 所有查询强制带 `class_id` 过滤；学生临时会话只能读 `user_id = self`（防 IDOR）；**手表请求的 `user_id` 一律由 token 反查**，唯一例外 `borrow` 需额外校验"本班 + active" |
| 权限校验 | 在服务端逐接口校验，前端隐藏按钮不作为安全手段 |
| 未成年人信息 | **最小化采集**：仅姓名、学号、班级；不采集身份证、住址、人脸、成绩 |
| 家长联系方式 | **不采集**（Q2 取消家长端），系统内无任何家长字段 |
| 数据出境 | 无，全部境内存储 |
| 告知义务 | 提供《家长告知书》模板（收集范围、用途、保存期限、删除方式） |
| 删除权 | 支持导出与删除；离班学生数据可选择性匿名化 |
| 日志 | 审计日志保留 1 年；不含敏感字段明文 |

> 说明：班级图书角属于学校日常教学管理场景，但仍建议做一次家长告知（一页纸即可），明确"只记录谁借了哪本书"。这既是合规要求，也能避免家长对"孩子阅读记录被记录"的顾虑。

### 9.3 可用性与降级

| 故障 | 影响 | 降级方案 |
|---|---|---|
| 断网 | 无法提交 | 离线队列，操作不丢，恢复后自动补交 |
| 服务端宕机 | 全部不可用 | 纸质登记表模板（打印好的表格），事后补录 |
| 扫码枪故障 | 扫码变慢 | 摄像头扫码 → 手输条码后 4 位 → 手输书名 |
| 打印机故障 | 无法打印标签 | 先入库，标签后补；临时用马克笔写在书脊 |
| 手表不可用（没电/丢失/未绑定） | 移动盘点与现场还书不可用 | 回一体机操作；**账目与提醒不受任何影响**（提醒主要靠大屏） |
| 手表离线（WiFi 掉线） | 手表无法上报 | 手表端明确提示"请到借还台操作"；盘点本地暂存并显示未上报数 |
| 推送通道故障 | 提醒不达 | 降级到次日大屏 + 纸质书签；逾期数据仍然准确 |

### 9.4 可维护性

- **一键部署**：Windows 下双击 `start.bat`（首次安装依赖并注册服务），之后开机自启
- **配置外置**：所有规则在设置页可改，不需要改代码
- **日志**：按天滚动，保留 30 天，`/api/health` 可看状态（含手表最近在线时间）
- **升级**：替换发行目录 + 重启服务，数据库自动迁移（Drizzle migrate）
- **交接**：提供《管理员手册》（10 页内）+《故障排查卡》（1 页）+《值班学生操作卡》（1 张 A4，图示版）
