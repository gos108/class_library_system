# 导出链路调研：教室没有 WiFi 时怎么把 Excel 给老师

| 项 | 内容 |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-10-20 |
| 触发 | 评审方指出：教室一般没有 WiFi，现有"局域网 HTTP 下载"方案不成立 |
| 结论 | **不需要互联网。手机热点本身就是一个局域网** |
| 状态 | 待确认后改代码 |

---

## 0. 先纠正一个前提

原设计假设"手表和老师手机得连同一个 WiFi"。这个假设不成立，但由此推出的"所以要上互联网"也不成立。

> **没有 WiFi ≠ 没有局域网。** 任何一台手机开热点，就是一个完整的局域网：有网关、有 DHCP、设备之间可以互相访问。

所以真正的问题不是"要不要联网"，而是"谁开热点"。

| 方案 | 需要互联网 | 需要第三方 | 数据出境 | 老师是否必须到场 |
|---|---|---|---|---|
| **A 手表开热点** | ❌ | ❌ | ❌ | ✅ |
| **B 老师手机开热点** | ❌ | ❌ | ❌ | ✅ |
| **C 互联网临时网盘** | ✅ 手表耗流量 | ✅ | ⚠️ 是 | ❌ 可异步 |
| D 二维码分片 | ❌ | ❌ | ❌ | ✅ |

A 和 B 都比 C 简单、快、安全。C 唯一的优势是**异步**——老师不在场也能事后下载。这一点后面单独说。

---

## 1. 方案 A：手表自己开热点（首选）

### 1.1 技术上成立

Android 从 8.0（API 26）起提供 `WifiManager.startLocalOnlyHotspot()`，官方文档明确说明：

- 用途就是"让连接到该热点的同地点设备上的应用互相通信"
- **该网络无法访问互联网**（正好，我们不想要）
- 每个应用可发起一个请求，回调返回 `LocalOnlyHotspotReservation`，其中含 SSID、密码
- 权限要求：`CHANGE_WIFI_STATE` + `ACCESS_FINE_LOCATION`（targetSdk < 33 时）
  - 我们的 targetSdk 是 28 → 走 `ACCESS_FINE_LOCATION` 这条
  - 注意：需要定位权限，但可以加 `neverForLocation` 标记说明用途

**不消耗流量、不依赖 SIM 卡、不依赖任何外部服务。**

### 1.2 交互设计（关键在二维码）

手表屏幕只有 1.68 英寸，让老师手输 SSID + 密码不现实。用**两个二维码分步展示**：

```
第 1 屏：连热点
┌──────────────────┐
│  ① 扫码连这个 WiFi │
│  ┌────────────┐  │
│  │  [二维码]   │  │   内容是标准 WiFi 二维码：
│  └────────────┘  │   WIFI:T:WPA;S:BookCorner-8f2a;P:12345678;;
│  BookCorner-8f2a │
│  密码 12345678    │   Android / iOS 相机扫了会直接弹出"加入网络"
└──────────────────┘
         ↓ 连上后
第 2 屏：下载
┌──────────────────┐
│  ② 打开这个地址    │
│  ┌────────────┐  │
│  │  [二维码]   │  │   http://192.168.43.1:8080/r?t=abc123
│  └────────────┘  │
│ 192.168.43.1:8080│
└──────────────────┘
```

**WiFi 二维码是这套交互的关键**——它把"手输 12 位密码"变成"扫一下自动加入"。手机连上后会提示"此 WLAN 无法访问互联网，是否保持连接"，选"保持"即可。

> 如果两个二维码分开显示体验仍不够好，可以在同一屏竖排两个小码（各约 0.7 寸），但扫码成功率会下降。建议先做分步。

### 1.3 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **厂商 ROM 禁用** | 小米/honor 等定制系统可能限制应用创建热点。公开资料里 `startLocalOnlyHotspot` 是官方 API，但儿童手表固件可能裁剪 | **必须 PoC**（见第 5 章） |
| 与手表 WiFi 冲突 | 部分设备开热点时会断开 WiFi | 我们本来就不需要 WiFi，无所谓 |
| 耗电 | 热点功耗较高 | 只在导出页开启，页面退出即关闭；单次导出 1–2 分钟 |
| 门禁/校园网干扰 | 无关 | — |

## 2. 方案 B：老师手机开热点，手表连上（最稳的兜底）

如果 A 因为 ROM 限制做不了，B 几乎一定能成——因为它只要求手表能做一件最普通的事：**连 WiFi**。

```
老师手机开热点 → 手表在设置里连上（输一次密码，以后自动连）
              → 手表显示自己的 IP（如 192.168.43.17）
              → 老师手机浏览器打开 http://192.168.43.17:8080
              → 下载
```

| 优点 | 缺点 |
|---|---|
| 零特殊权限、零兼容性风险 | 老师要开热点，手表要输一次密码（后续记住） |
| 复用现有代码（HTTP 服务 + 二维码只改内容） | 手表 IP 每次可能变，必须显示出来 |
| | 部分安卓热点会做客户端隔离（同一热点下设备互不可见）——**需实测** |

> **客户端隔离这条要特别验证**：绝大多数 Android 热点默认不隔离，客户端之间可以互访。但个别 ROM 或"访客网络"会隔离。这是 B 方案唯一的致命点。

**实现成本**：几乎为零。现有 `NanoHTTPD` + 二维码方案不用改，只是把"局域网 IP"换成"热点内 IP"，并在页面上把 IP 用大字显示。

## 3. 方案 C：互联网临时网盘（调研结果：不建议）

### 3.1 文叔叔：没有公开 API

| 项 | 实际情况 |
|---|---|
| 官方 API | **没有**。官网只有网页端和 App，无开发者文档 |
| 现有实现 | GitHub 上有第三方逆向的 Python 客户端（`wenshushuR`，2023 年），用 base58 + `pycryptodomex`，说明接口带自定义加密，且每次上传生成新的 `X-TOKEN` |
| 匿名可用性 | 官网明示"未登录，对方无法在线预览"——匿名上传很可能拿不到可用的下载页 |
| 移植到 Kotlin | 要把 base58 + 自定义加密 + 抓包得到的私接口全复刻一遍，任何一次改版就全废 |
| 合规 | 服务条款通常禁止自动化调用 |

**结论：不可行。** 不是"难"，是"做完也不知道能活多久"。

### 3.2 有公开 HTTP API 的临时文件服务

这类服务的接口都很简单（一次 POST 拿回 URL），技术上可行：

| 服务 | 接口形态 | 保留期 | 国内可达性 |
|---|---|---|---|
| file.io | `POST` multipart → JSON `{link}` | 下载一次即删 | ⚠️ 不稳定 |
| tmpfiles.org | `POST` multipart → 返回 URL | 1 小时 | ⚠️ 未知 |
| 0x0.st | `POST` multipart → 纯文本 URL | 按大小 30–365 天 | ⚠️ 常被墙 |
| catbox / litterbox | `POST` multipart | litterbox 1–72 小时 | ⚠️ 未知 |

**但有三条硬伤，任何一条都足以否掉它：**

**① 数据出境与学生隐私。**
导出的 xlsx 里有全班学生姓名 + 每个人的借阅记录。这是未成年人个人信息。上传到一个国外的匿名临时网盘，等于把班级数据交给一个不受监管、且几分钟后就无法追溯的第三方。**这一条我认为是决定性的**，不是技术问题。

**② 手表的网络不一定可用。**
需要 SIM 卡有流量、信号好。教室在楼里，4G 可能只有一两格。而且流量费是家长出的。

**③ 服务不可靠。**
临时网盘靠广告/捐赠活着，说关就关（`transfer.sh` 就关过）。一个班级工具依赖它，等于把"能不能交报表"交给一个随时可能消失的服务。

### 3.3 如果确实要"上云"，正规做法是对象存储

真要异步交付，正确选择不是临时网盘，而是**腾讯云 COS / 阿里云 OSS**：

| 优点 | 代价 |
|---|---|
| 有稳定 API、国内速度快、几分钱一个月 | 要配 bucket + 密钥 |
| 可设 1 天过期、私有读 | 密钥存在手表 App 里 = 泄露风险 |
| 数据在境内、可审计 | 增加运维负担 |

**我的判断**：为一个班级图书角配 OSS + 密钥管理，成本远高于收益。除非将来要做多班共用。

### 3.4 C 唯一的真实优势

**异步**。A/B 都要求老师此刻在场；C 可以让学生上传后，把链接通过手表微信发给老师，老师晚上在家下载。

但要清楚代价：为了这个便利，要付出"数据出境 + 依赖不可靠服务 + 消耗家长流量"三项。**除非老师明确说自己经常不在教室，否则不值得。**

## 4. 方案 D：二维码分片（最后兜底）

数据量算一下：800 册 + 2000 条借阅 ≈ 300KB JSON，gzip 后约 40KB。

- 每片二维码承载约 1KB → **约 40 个二维码**
- 而且要在 1.68 英寸屏上逐屏翻 40 次，老师逐张扫

**不可行**，只在"设备完全没有任何网络能力"时才考虑，且只适合导出"在借清单"这种小数据集（20 条以内，2–3 个码）。

## 5. 推荐与实施

### 5.1 结论

```
首选 A（手表开热点）
  └─ PoC 失败 ──→ B（老师手机开热点）
                    └─ 客户端隔离导致不通 ──→ 改回 A 的变通：老师用 USB 取文件？（不可行）
                                              → 最后才考虑 C
```

**A 与 B 的代码差异极小**：都复用现有的 `NanoHTTPD` + 二维码，只是页面文案和 IP 来源不同。所以**两个都实现、运行时自动选择**，成本最低：

```
点「生成报表」
  ↓
尝试 startLocalOnlyHotspot()
  ├─ 成功 → 显示热点 SSID/密码二维码 + 下载地址二维码（A）
  └─ 失败 → 提示"请让老师开热点，并连上"→ 显示本机 IP 二维码（B）
```

### 5.2 对现有代码的影响

| 模块 | 影响 |
|---|---|
| 数据层 / 状态机 / 借还 | **零影响** |
| `NanoHTTPD` 服务 | 零影响，照旧监听 8080 |
| 报表页 | 重写：从"显示一个 IP"变成"A/B 两态 + 两个二维码" |
| AndroidManifest | 加 `CHANGE_WIFI_STATE`、`ACCESS_FINE_LOCATION` |
| 二维码生成 | 需要引入一个小库（约 30KB）生成 WiFi 码与 URL 码 |

### 5.3 必须验证的 PoC

| 编号 | 验证项 | 判定 | 影响 |
|---|---|---|---|
| **P7** | 米兔 7 能否 `startLocalOnlyHotspot` | 回调拿到 SSID/密码 = 通过 | 决定 A 是否可用 |
| **P8** | 安卓手机连手表热点后，能否访问 `192.168.43.1:8080` | 能打开页面 = 通过 | A 的最后一环 |
| **P9** | 老师手机开热点，手表连上后，手机能否访问手表 IP | 能打开 = 通过 | 决定 B 是否可用 |
| P10 | 热点开启期间手表的 4G 是否还通 | 通/不通都行 | 只影响是否需要"导出时不需要外网"的说明 |

> P7 和 P9 至少要通过一个，否则整个导出链路要重新设计。

## 7. 一句话结论

> **不要为了"没有 WiFi"去上互联网。手机热点就是一个局域网，而且它更快、更安全、不花钱、不依赖任何第三方。**
>
> 文叔叔这类临时网盘没有公开 API，逆向实现不可维护；更关键的是，把全班学生的姓名和借阅记录上传到匿名临时网盘，这个代价不该由一个小工具来付。

**待你确认**：按 A+B 双实现（运行时自动降级）来做，还是只做 B（最稳、代码最少）？
