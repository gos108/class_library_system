## 1. 安装与入口：调研结论

> 以下基于公开资料整理，**必须以实机验证为准**（第 10 章 P1）。但方向性判断已经足够清晰。

### 1.1 官方只有一条路：厂商应用商店

米兔手表的应用分发是**厂商审核制**，公开资料一致描述为：

```
米兔 App（家长端）→ 我的 → 应用商店 → 选择应用 → 下载
   ↓（下载安装时手表必须接充电器）
手表：回到表盘界面 → 按电源键 → 进入应用列表 → 点图标启动
```

| 事实 | 说明 |
|---|---|
| 应用商店里的应用 | 口袋故事、吉米猫英语、新华字典、趣味加减法、QQ、微信儿童版等**教育/社交类合作应用** |
| 第三方能否自行上架 | 需要企业主体 + 与小米/小寻的商务合作。**个人开发者没有提交入口** |
| 能否侧载 | 官方渠道明确不支持。安装包受签名校验 |
| 应用入口位置 | 表盘 → 电源键 → 应用页。**没有桌面快捷方式概念** |

**结论：官方路径走不通。** 不是技术问题，是没有对个人的开放通道。

### 1.2 确认机型：米兔儿童学习手表 7

**型号 MTSB24XUN，2024 年 3 月上市，官方定价 799 元。**（同代还有 7X，是低配版：512MB+4GB、无健康监测）

| 参数 | 米兔 7（你的机型） | 说明 |
|---|---|---|
| 屏幕 | 1.68" IPS TFT，**360×390** | 比 6C 的 240×240 高一个档次 |
| 内存 / 存储 | **1GB RAM + 8GB ROM** | 跑原生 App + SQLite 绰绰有余 |
| 摄像头 | **前置 500 万 + 侧置 800 万** | **侧置摄像头对扫码非常有利**——手不用扭 |
| 系统 | 官方未明示，**大概率 Android 底座** | 支持微信儿童版 / 支付宝 / QQ，有应用商店 |

### 1.3 关键动作：先在你的手表上验证一次（10 分钟）

> 这一步不做，后面全是猜。**P0，优先于所有其他工作。**

**验证逻辑（不是操作教程，是判定路径）**：目标只有一个——**确认这台手表能不能装一个非应用商店来源的 APK**。

需要依次确认四个问题，任何一个"否"就到此为止：

| # | 要确认的事 | 判定的意义 |
|---|---|---|
| V1 | 设置里能否进入**售后/测试页**（通常需要输入密码） | 进不去 → 没有开发者入口，路线乙终结 |
| V2 | 测试页里能否看到**开发者选项 / USB 调试 / 三方应用** | 没有 → 同上 |
| V3 | 用数据线连电脑后，`adb devices` 能否识别到设备 | 识别不到 → 同上 |
| V4 | `adb install` 一个空白测试 APK 是否成功，装完能否启动 | 装不上或起不来 → 需要第三方启动器，难度上升但仍可能 |

**如果 V1–V4 全部通过** → 走**路线乙**，这是最优解：原生 Android + SQLite + 8GB 存储 + 800 万侧摄，完全满足设计。

**如果任一项失败** → 走**路线甲或丁**（见 1.4）。

> ⚠️ **必须先读这段再动手**：
> - 这是**儿童安全设备**，定位、通话、SOS 是它的核心价值。任何改动一旦影响这些功能，代价远超一个图书角系统。
> - 公开资料显示 4Pro 的售后页入口需要特定密码，各机型不同；7 的密码**未见公开记录**，可能需要联系售后或自行摸索。**找不到不要硬试**，反复输错可能触发锁定。
> - 变砖、失去保修、家长端异常，都是真实存在的后果。
> - **我的建议**：如果 V1 就走不通，**立刻停止**，不要为了一个班级工具去折腾孩子的手表。

### 1.4 四条路线

| 路线 | 做法 | 前提 | 成本 | 可复制性 | 推荐 |
|---|---|---|---|---|---|
| **乙** | **米兔 7 原生 APK**（SQLite） | 1.3 的 V1–V4 全过 | 0 元 | 差（只这一台） | ★★★★ **若验证通过，首选** |
| **甲** | 教室固定一台安卓手机/平板（PWA） | 有一台闲置安卓 8.0+ 设备 | 0–400 元 | 好 | ★★★★★ **验证失败则首选** |
| **丁** | 另购**开放 Android 手表**（AOSP，可自由装 APK） | 无 | 200–500 元 | 中 | ★★★ 想保留"手表形态"时的折中 |
| 丙 | 等厂商应用商店上架 | 需企业资质 + 商务合作 | — | — | ✘ 不可行 |

**关于路线甲的一个常见误解**

> "手机不能进校园，所以只能用手表。"

这条约束在**图书角场景里其实不成立**——图书角是教室里的**固定角落**，借还都发生在那儿，采集设备**不需要随身佩戴**，放在书架旁即可。只有盘点时需要走动，而盘点一个月才一次，拿个平板走过去完全没问题。

真正需要"随身"的是安全与通讯，那是手表的本职，不该让图书管理来挤占。

**关于路线丁（如果你坚持要手表形态）**

市面上存在**开放 Android 手表**（AOSP 底座，可自由安装 APK），公开资料里能查到的例子包括华强北 M89H 类（4GB+64GB、4G、可装任意 APK，百元级）、运营商定制的 And Watch W1A（骁龙 Wear 2100、512MB+4GB、1.4" 400×400、可通过 ADB 装第三方应用，二手 70 元左右）。

| 优点 | 缺点 |
|---|---|
| 真正的手表形态，盘点时最方便 | 质量与续航不可控，可能三个月就坏 |
| 原生 Android + SQLite，开发最顺 | 不适合当儿童通讯设备（但这台也不需要） |
| 不碰孩子的米兔，零风险 | 需要一个额外的采购决策 |

> **关键认知**：这台设备**不需要是儿童通讯手表**。它只要"能装 APK + 有摄像头 + 有 WiFi"，不需要插卡、不需要定位、不需要防水。把它当"图书角专用扫码终端"来选型，选择面会宽很多。

### 1.5 路线乙的风险清单（若 V1–V4 通过，动手前必读）

| 风险 | 后果 |
|---|---|

## 2. 存储选型：先算数据量，再选技术

### 2.1 这个系统的数据到底有多大

| 实体 | 数量级 | 单条 JSON 估算 | 合计 |
|---|---|---|---|
| member（名册） | 45 | 60 B | 2.7 KB |
| book（书目） | 300 | 120 B | 36 KB |
| copy（册） | 800 | 90 B | 72 KB |
| loan（借还记录） | 5 年约 2000–5000 | 80 B | 160–400 KB |
| op_log（操作流水） | ≤ loan 的 2 倍 | 50 B | ≤ 400 KB |
| **合计** | | | **约 0.3–0.9 MB** |

**关键结论：整个数据库不到 1MB。**

这个数字改变了一切选型逻辑：

> **容量根本不是问题。真正的问题是两件别的事：① 沙箱会不会把数据清掉；② 数据能不能拿出来。**

任何声称"因为容量/性能所以要上 SQLite / NoSQL"的理由，在这个数据量下都不成立。

### 2.2 候选方案逐一评估

| 方案 | 容量 | 持久性 | 能否导出 | 依赖体积 | 适用运行时 | 评价 |
|---|---|---|---|---|---|---|
| **localStorage** | 5MB | ⚠️ 中，WebView 清理策略下可能被清 | ✔ 取字符串即可 | 0 | WebView | 够用，但同步阻塞、易被清 |
| **IndexedDB** | 数百 MB | ⭕ 较好，比 localStorage 稳 | ✔ 可导出 JSON | 0 | WebView | **WebView 首选** |
| **SQLite** | 取决于分区 | ✅ 最好，事务安全 | ✔ 直接拿 `.db` 文件 | 系统自带 | 原生 Android | **原生首选** |
| **文件系统（JSON 文件）** | 大 | ⭕ 好 | ✔ 就是个文件 | 0 | 原生 Android | 简单可靠，次选 |
| **PouchDB / LokiJS / NeDB** | 大 | ⭕ | ✔ | **+100–200KB** | WebView | ✘ 在这个数据量下纯属负担 |
| **云同步（Firebase 等）** | — | ✅ | — | — | 任意 | ✘ 违背"数据在本地" |
| **SQLite WASM + OPFS** | 大 | ⭕ | ✔ | **+1MB 以上** | Chrome | ✘ 为一个 1MB 的库引入 1MB 的引擎，不划算 |

**关于 "其他 NoSQL"**：IndexedDB 本身就是 NoSQL（键值 + 对象存储）。再往上叠 PouchDB/CouchDB 这类文档库，收益是"同步能力"——而我们明确不要同步。在这个数据量下，**多引入一个库只会增加体积和不确定性**。所以答案很直接：**不需要任何额外的 NoSQL 方案。**

### 2.3 推荐方案（分运行时）

#### 运行时 A：原生 Android（路线乙，或将来上架）

> **SQLite**。直接、标准、可靠。
> - 800 册 + 5000 条记录对 SQLite 是小菜，写入 < 5ms
> - 事务天然保证"借出 + 改状态 + 写流水"三步原子
> - 备份 = 复制一个 `.db` 文件；导出 = 按查询生成 xlsx
> - 无任何第三方依赖

#### 运行时 B：WebView / PWA（路线甲）

> **IndexedDB，但只用"一个键存一个 JSON"这种最笨的用法**，配**双槽轮换写入**。

很多方案会建议把每张表建成一个 object store、加索引、写事务。**在这个数据量下这是过度设计**：数据一共 1MB，全量读进内存也就几十毫秒，内存里做筛选排序比索引快得多。

**双槽机制（抗半写损坏）**

```
存储里只有两条记录：
  slot_a = { seq: 12, checksum: "…", payload: "<整个库的 JSON>" }
  slot_b = { seq: 11, checksum: "…", payload: "<上一个版本>" }

写入流程：
  1. seq 取两槽最大值 +1
  2. 写入「seq 较小的那一槽」（即较旧的那槽，不会破坏最新数据）
  3. 写完回读，校验 checksum
  4. 校验失败 → 重试一次；仍失败 → 报警并保留旧槽

读取流程：
  1. 读两槽
  2. 各自校验 checksum
  3. 取「校验通过 且 seq 最大」的那一槽
```

| 为什么这么做 | 说明 |
|---|---|
| 抗断电/崩溃 | 写 A 时崩了，B 仍是完整的上一版；反之亦然 |
| 模型极简 | 没有表、没有索引、没有事务 API，只有"读一个字符串、写一个字符串" |
| 可移植 | 同一套逻辑能换成 localStorage、文件、甚至 SQLite 的一个 TEXT 字段 |
| 备份直接 | 导出的就是这一串 JSON，人可读、可校验 |
| 校验成本 | 1MB 做一次简单校验和，< 5ms，无感 |

**写入时机**：每次业务操作后立即写（或 300ms 内合并写一次）。800 册的库一次全量写约 10–30ms，交接班级别的操作频率完全无压力。

### 2.4 存储方案对比小结（结合米兔 7 的结论）

| 问题 | 答案 |
|---|---|
| **米兔 7 上该用什么** | **取决于路线**：<br>· 走乙（原生 APK）→ **SQLite**，8GB 存储完全够，`.db` 文件直接备份<br>· 若将来只能跑 WebView → **IndexedDB 单键 JSON + 双槽** |
| IndexedDB 合适吗 | **合适**，是 WebView 下最优选择。但要用"单键 JSON + 双槽"，不要用多表多索引 |
| SQLite 如何 | **原生 Android 下明显更好**：事务原子、备份=复制文件、导出按查询走。WebView 里用不了（WASM 引擎比数据大十倍） |
| 其他 NoSQL 呢 | 不需要。数据 < 1MB，PouchDB 之类只会增加体积和不确定性 |
| 1GB RAM 够吗 | **够**。整个库不到 1MB，SQLite/IDB 的常驻开销在 10MB 量级，剩下 990MB 富余 |
| 8GB 存储够吗 | **绰绰有余**。库 1MB + 备份 7 份 + 应用本体，合计 < 50MB |
| 最该担心什么 | **不是选型，是持久性**。沙箱/系统会不会清数据，必须实测（P2） |

> **一句话结论**：以米兔 7 的硬件（1GB+8GB），**存储选型没有任何技术风险**。若走原生就 SQLite，走 WebView 就 IDB 单键；两者都不需要引入任何第三方数据库。

## 3. 书籍状态机（4 态）

### 3.1 四个状态

| 状态 | 代码值 | 含义 | 谁触发 |
|---|---|---|---|
| **入库** | `in` | 书在图书角、可借出 | 同学带书来，扫描 + 语音登记所有者 |
| **借出** | `out` | 已被某同学借走 | 来图书管理员处登记 |
| **遗失** | `lost` | 借出后确认找不到了 | 图书管理员手工变更（需班主任事后确认） |
| **出库** | `removed` | 其他原因离开图书角（所有者取回等） | 手工变更 |

> 注意"入库"的语义：它不只是"入册"这个动作，而是**当前处于"在库可借"这个状态**。归还后也回到"入库"。

### 3.2 状态流转

> 共 8 条转移（T1–T8），完整规则见 3.3 的表格。这里只强调三条"回边"——它们是最容易被忽略、也最容易造成账目混乱的地方：

| 回边 | 场景 | 处理 |
|---|---|---|
| 借出 → 入库 | 正常归还 | 结单，状态回 `in` |
| **遗失 → 入库** | 以为丢了，后来找到了 | 恢复状态，但**保留原 loan 的 lost 历史**，不删记录 |
| **出库 → 入库** | 所有者取回后又带回来了 | 恢复状态，不新建副本（条码复用） |

### 3.3 流转规则表

| # | 从 | 到 | 触发 | 必填 | 落库动作 |
|---|---|---|---|---|---|
| T1 | （新建） | 入库 | 扫描/语音录入 | 书名、分类、**所有者** | 建 book + copy |
| T2 | 入库 | 借出 | 借出登记 | **借出人** | 建 loan，`copy.status=out` |
| T3 | 借出 | 入库 | 归还登记 | — | 结 loan，`copy.status=in` |
| T4 | 借出 | 遗失 | 手工 | 备注（可选） | 结 loan（标记 lost），`copy.status=lost` |
| T5 | 入库 | 出库 | 手工 | 原因（所有者取回 / 破损 / 其他） | `copy.status=removed` |
| T6 | 借出 | 出库 | 手工 | 原因 | 先结 loan，再 `removed` |
| T7 | 遗失 | 入库 | 手工撤销 | 备注 | `copy.status=in`（loan 保持 lost 历史） |
| T8 | 出库 | 入库 | 重新带回 | — | `copy.status=in` |

**规则约束**

- **T4/T5/T6 只能由图书管理员操作，且必须填写原因**。这三个是"账目消失"的路径，最容易被误用，所以强制留痕。
- **T7（撤销遗失）不删除原 loan 记录**，只恢复副本状态。历史必须完整——"曾经以为丢了"本身是事实。
- 出库/遗失的书**不再出现在借出流程的候选中**，但**保留在导出清单里**（老师需要知道"这本书去哪了"）。
- 不设"删除"。任何书都不从库里消失，只有状态变化。

## 4. 总体架构

> 架构与路线无关：**采集端（唯一数据源）+ 导出网关（转换器）**。路线只决定"采集端跑在什么设备上、用什么存储"。

```
┌──────────────────────────────────────────────────┐
│  采集端（二选一，业务代码一致）                       │
│  ┌────────────────────────────────────────────┐  │
│  │  A 米兔 7 · 原生 APK（若 P0 通过）            │  │
│  │     存储：SQLite（8GB 存储，绰绰有余）         │  │
│  ├────────────────────────────────────────────┤  │
│  │  B 安卓手机/平板 · PWA（P0 未通过时）          │  │
│  │     存储：IndexedDB 单键 JSON 双槽            │  │
│  └────────────────────────────────────────────┘  │
│  共同能力：摄像头扫码 · 语音输入 · 离线可用           │
└───────────────────────┬──────────────────────────┘
                        │ 仅"生成报表"时，局域网发送
                        ▼
┌──────────────────────────────────────────────────┐
│  导出网关：教室电脑（单文件 exe，双击运行）            │
│  接收 → 生成 3 sheet 的 xlsx → 存桌面              │
└───────────────────────┬──────────────────────────┘
                        ▼
                    微信发送 / U 盘 / 打印
```

**两条路线的差异只在采集端内部**：UI 代码可复用，差异集中在三处——存储适配层（SQLite / IndexedDB）、扫码库（原生 Camera2 / zxing-wasm）、语音入口（系统 ASR / Web Speech）。**状态机、数据模型、语音匹配算法、导出格式完全相同**，这也是本设计把业务逻辑与运行时解耦的原因。

## 6. 交互设计（去掉战损后）

### 6.1 首页

```
┌────────────────┐
│ 共 312 本       │
│ 在库 294 借出 18 │
├────────┬───────┤
│  入 库  │ 借 出  │
├────────┼───────┤
│  归 还  │ 查 书  │
└────────┴───────┘
    [ 更多：遗失 / 出库 / 报表 ]
```

### 6.2 入库（扫 + 说所有者）—— 本方案语音的主场景

| 步 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点「入库」→ 扫码 | 扫 ISBN 或已有条码 |
| 2 | — | 有 ISBN：自动带出书名/作者/出版社<br>无 ISBN：提示「说书名」，识别后确认 |
| 3 | 选分类（4 个色块） | 必填 |
| 4 | **语音说所有者**：「王小明」 | 在 45 人名单里模糊匹配，显示「所有者：王小明」 |
| 5 | 若匹配到多人 | 列 2–3 个候选点选 |
| 6 | 点「入库」 | 生成内部条码，状态 `in`，可打印标签 |

> 目标耗时：有 ISBN **20–30 秒/本**；无 ISBN **30–40 秒/本**。

### 6.3 借出（扫 + 说借出人）

| 步 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点「借出」→ 扫码 | 扫书码 |
| 2 | — | 显示书名；若非 `in` 状态，直接提示「这本书已借出/已遗失」 |
| 3 | 语音说「王小明」 | 匹配 → 显示「王小明 借《夏洛的网》」 |
| 4 | 点「确定」 | 建 loan，`copy.status=out`，`due_at=+14 天` |

**目标耗时：8–12 秒。**

### 6.4 归还（扫 + 确认）—— 比 v1.0 少一步

| 步 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点「归还」→ 扫码 | 反查 active loan |
| 2 | — | 显示「王小明 · 11月2日应还」 |
| 3 | 点「收下了」 | 结 loan，`copy.status=in` |

**目标耗时：4–6 秒。**（v1.0 因为要采集战损，是 8 步；现在少了最重的一步）

### 6.5 遗失 / 出库（手工，带原因）

| 步 | 操作 | 系统行为 |
|---|---|---|
| 1 | 首页「更多」→「遗失」或「出库」 | — |
| 2 | 扫码或从在借列表里选 | — |
| 3 | 选原因（所有者取回 / 破损 / 确认丢失 / 其他） | 必填 |
| 4 | 二次确认「这本书将从借阅中移除」 | 防误操作 |
| 5 | 确认 | 改状态，写 op_log |

### 6.6 语音识别策略（不变，且更重要了）

**不做开放听写，做"受限词表 + 模糊匹配"。**

| 识别目标 | 候选空间 | 策略 |
|---|---|---|
| **人名**（所有者、借出人） | **仅 45 个** | 拼音模糊匹配，四级降级 |
| 册数 | 1–10 | 数字词表 |
| 书名 | 无限 | 开放文本，允许错字，人工确认 |
| 出库原因 | 4 个 | 点选，不用语音 |

**人名匹配四级降级**

| 级 | 规则 | 例 |
|---|---|---|
| 1 | 完全相等 | 王小明 |
| 2 | 无声调拼音相等 | `wangxiaoming` |
| 3 | 首字母相等 | `wxm` |
| 4 | 拼音编辑距离 ≤ 2 | 误识为"王晓明"仍可命中 |

> 语音原始准确率 70–80%，但候选只有 45 个，经拼音归一 + 编辑距离后命中率可达 95%+，失败还有候选点选兜底。
>
> 去掉战损后，语音的用途反而更聚焦：**全部集中在"人名"这一件事上**——而这正是模糊匹配最擅长的场景。

### 6.7 若语音不可用

降级为「最近 8 人快选 + 首字母筛选」。功能不缺，只是从 2 秒变成 5 秒。

## 9. 导出链路（不变）

```
采集端点「生成报表」→ 同一 WiFi → POST 到网关 → 生成 xlsx 到桌面 → 微信发送
```

**米兔 7 的网络限制（走路线乙时必须注意）**

> 米兔 7 的 WiFi 规格是 **2.4GHz**（不支持 5GHz）。而同代产品普遍**不支持企业级加密 WiFi（802.1X）**，学校网络大多使用这种认证方式。
>
> 解决：用老师/家长的手机开 **2.4GHz 个人热点**（WPA2-Personal），手表连热点、电脑也连热点。导出一分钟完成，不需要长期联网。
