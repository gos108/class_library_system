## 0. 定稿了什么

评审方给出的方案基线，本设计全部照此执行：

| # | 定稿内容 | 对 v0.3 的影响 |
|---|---|---|
| 1 | 记录**书籍 / 所有人 / 借还状态 / 借还人 / 战损程度** | 这是全部数据范围，不做扩展 |
| 2 | 充分利用手表的**扫描 + 语音**完成录入与借还 | 语音从"可选项"升级为**核心输入方式** |
| 3 | 数据存储在 **app 本地** | 删除服务端、数据库、部署、备份服务器等全部内容 |
| 4 | **不做归还提醒** | 删除 M4 整个模块、reminder 表、推送通道、班级大屏 |
| 5 | 老师要看时**导出 Excel** 发送 | 导出成为唯一对外交付物，需重点设计 |

**因此本设计相比 v0.3 砍掉了**：逾期提醒、家长端、推送服务、Web 管理端（大部分）、统计报表模块、预约、异常队列、审计日志（简化为操作流水）、多端同步与冲突处理、服务器部署与备份。

**保留并加强**：书籍与副本、成员名册、借还核心、**战损登记**、**手表扫描与语音**、**Excel 导出**。

> 一句话：从一个"班级图书管理系统"收缩成一个"图书管理员的随身工具 + 一份能发给老师的 Excel"。

## 1. 一处必须先说清的硬约束

> 这一节不是技术保守，而是避免把工期投在一个做不出来的功能上。

### 1.1 "手表上的微信把 Excel 发给老师"大概率不可行

| 环节 | 现实情况 | 判断 |
|---|---|---|
| 微应用生成 `.xlsx` 文件 | H5 容器内可以生成二进制（SheetJS） | ⚠️ 可生成，但**存哪里**是问题 |
| 把文件交给系统 / 微信 | 微应用沙箱一般不开放系统分享、文件选择器、Intent 调用 | ❌ **大概率不通** |
| 微信儿童版接收/发送文件 | 儿童版微信定位是语音与简短消息，**不支持文件传输** | ❌ 不通 |
| 手表存储空间 | 通常 4–8GB，微应用沙箱配额很小 | ⚠️ 不宜存大量报表 |

**结论：不要设计"手表直接发文件"的链路。** 这需要 PoC 推翻（见第 11 章 P5），但不能作为方案前提。

### 1.2 推荐链路：手表生成 → 教室电脑承接 → 微信发送

```
手表（唯一数据源）
  │  点"生成报表" → 打包 JSON（gzip）→ 局域网 POST
  ▼
教室电脑上的"导出网关"（单文件小程序，双击运行）
  │  收数据 → 生成 3 个 sheet 的 xlsx → 存到桌面
  ▼
老师/学生用电脑上的微信发送  ← 这一步是普通文件发送，无任何技术障碍
```

**为什么这样切**：

| 理由 | 说明 |
|---|---|
| 数据仍然只在手表 | 电脑只是"打印店"，收完即转成 xlsx，不长期存储，不构成第二个数据源 |
| 导出是低频动作 | 一周/一月一次，多走一步电脑完全可以接受；日常借还**完全不需要电脑在线** |
| 微信发文件在电脑上是原生能力 | 不依赖任何厂商开放接口 |
| 零成本、零账号、零月费 | 仍然是纯本地 |

### 1.3 兜底：连电脑都没有时

手表把数据压缩后**分片生成二维码**，老师用手机扫码重组，再由接收页生成 xlsx。

- 数据量估算：300 册 + 800 条借还 ≈ 60KB JSON → gzip 后约 8–12KB
- 每片二维码承载 ~1KB → 约 **10 个二维码**，老师扫 10 次
- 笨，但零依赖，作为最后退路

> 设计原则：**把网络依赖压缩到只剩"导出"这一个低频动作**。日常录入、借、还、查，全部离线在手表内完成。

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│  米兔手表（图书管理员持有，仅 1 台）                        │
│  ┌───────────────────────────────────────────────────┐  │
│  │  微应用「图书角」                                    │  │
│  │  · 摄像头扫描（ISBN / 内部码）                        │  │
│  │  · 语音输入（人名 / 册数 / 战损）                      │  │
│  │  · 本地存储（IndexedDB，唯一数据源）                   │  │
│  │  · 离线可用，无需网络                                 │  │
│  └───────────────────────────────────────────────────┘  │
└────────────────────────┬────────────────────────────────┘
                         │ 仅"生成报表"时，局域网 POST（JSON+gzip）
                         ▼
┌─────────────────────────────────────────────────────────┐
│  教室电脑「导出网关」（单文件 exe，双击运行，零安装）        │
│  · 接收数据 → 校验 → 生成 xlsx（3 个 sheet）              │
│  · 落盘到桌面：班级图书角_20261020.xlsx                   │
│  · 不留存业务数据（转完即弃）                              │
└────────────────────────┬────────────────────────────────┘
                         │ 普通文件
                         ▼
                    老师微信 / U 盘 / 打印
```

**三个关键取舍**

| 取舍 | 决定 | 理由 |
|---|---|---|
| 有没有服务端 | **没有** | 数据在 app 本地，无同步、无账号、无并发，也就没有冲突处理这一整类问题 |
| 手表是否依赖网络 | **日常完全不依赖** | 只有导出需要 WiFi；断网不影响借还，只影响出报表 |
| 导出网关是否存数据 | **不存** | 避免出现"第二份真相"，用户永远只有手表这一个数据源 |

## 3. 数据模型

### 3.1 实体关系

```
  member（所有人 / 名册）
     │ 1:N                        ┌──────────┐
     ├───────────────────────────►│  loan    │ 借还记录
     │        （借还人）            └────┬─────┘
     │                                   │ N:1
     │ 1:N                               ▼
     └───────────────────────────►  copy（册）◄─── book（书目）
              （书籍归属人，可空）        │ 1:N          │ 1:N
                                        │              ▼
                                        │         category（分类）
                                        ▼
                                  condition_log（战损变更）

  op_log（操作流水，用于追溯"谁在什么时候做了什么"）
```

### 3.2 member（所有人 / 名册）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| name | TEXT | 姓名 |
| pinyin | TEXT | **全拼，无声调**（如 `wangxiaoming`）——语音匹配的核心 |
| initials | TEXT | 首字母（如 `wxm`） |
| role | TEXT | `student` / `librarian` / `teacher` |
| status | TEXT | `active` / `left` |
| created_at | DATETIME | |

> `pinyin` 与 `initials` 在导入名单时自动生成。**这两个字段直接决定语音借书的可用性**，不能省。

### 3.3 book（书目）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| isbn | TEXT NULL | 可空（旧书/无条码书） |
| title | TEXT | 书名（必填） |
| author | TEXT | 作者（可空） |
| publisher | TEXT | 出版社（可空） |
| category_id | INTEGER FK | 分类 |
| cover_url | TEXT | 封面（可空，手表端不展示，导出时可带） |
| source | TEXT | `scan`（扫 ISBN 带出）/ `voice`（语音录入）/ `manual` |
| created_at | DATETIME | |

### 3.4 copy（册 · 核心表）

> **书目与册必须分离**。同一本书 5 册就是 1 条 book + 5 条 copy。否则"还剩几本在架""这册书是谁弄坏的"都无法回答。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| book_id | INTEGER FK | 所属书目 |
| barcode | TEXT UNIQUE | 内部码（9 位，扫 ISBN 后自动生成） |
| status | TEXT | `available` 在架 / `borrowed` 借出 / `lost` 丢失 / `retired` 注销 |
| **condition** | INTEGER | **战损程度 1–5**，见第 4 章 |
| **owner_member_id** | INTEGER FK NULL | **书籍归属人**（谁带来的书）；空 = 班级公共 |
| shelf | TEXT | 书架位，如 `A-3` |
| acquired_at | DATE | 入藏日期 |

> **关于"所有人"一词的两种理解，本设计同时兼容**：
> ① 若指**全体成员名册** → `member` 表承载；
> ② 若指**每本书的归属人**（学生带来的书，期末要还回去）→ `copy.owner_member_id` 承载。
> 两者并存不冲突，若实际只用其一，另一个保持空即可。

### 3.5 loan（借还记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| copy_id | INTEGER FK | 哪一册 |
| member_id | INTEGER FK | **借还人** |
| borrowed_at | DATETIME | 借出时间（手表本地时间，秒级） |
| due_at | DATE | 应还日期（默认 +14 天，**仅用于标记超期，不推送任何提醒**） |
| returned_at | DATETIME NULL | 归还时间 |
| **condition_before** | INTEGER | 借出时战损 |
| **condition_after** | INTEGER NULL | 归还时战损 |
| status | TEXT | `active` / `returned` / `lost` |
| operator_id | INTEGER FK | 操作人（通常是图书管理员） |

### 3.6 condition_log（战损变更留痕）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| copy_id | INTEGER FK | |
| loan_id | INTEGER FK NULL | **关联到具体某次借阅** |
| from_level / to_level | INTEGER | 变更前后 |
| note | TEXT | 备注（可选，语音录入） |
| created_at | DATETIME | |

> 这张表回答的是老师最关心的问题：**"这本书是什么时候、在谁手上变坏的"**。没有它，战损就只是一个静态数字，无法追溯。

### 3.7 op_log（操作流水）

| 字段 | 类型 | 说明 |
|---|---|---|
| id / action / target_type / target_id / operator_id / created_at | | 记录录入、借、还、改战损、注销等动作 |

## 4. 战损程度设计

### 4.1 五级制

| 级别 | 名称 | 判定标准（给孩子看的白话） | 是否可借 |
|---|---|---|---|
| 1 | 完好 | 跟新的一样 | ✔ |
| 2 | 轻微磨损 | 书角有点卷，不影响看 | ✔ |
| 3 | 明显磨损 | 书脊松了、纸发黄、有水渍 | ✔（导出时标记"关注"） |
| 4 | 破损可读 | 缺页、封面快掉了、装订开裂 | ✔ 但**导出时进"待修补"清单** |
| 5 | 不可流通 | 烂得没法看 | ✘ 自动转 `retired` 待处置 |

**为什么是 5 级而不是 10 级**：判定人是 10 岁左右的孩子，级数越多判断越不一致。5 级且每一级都有"白话标准"，才能保证不同人判得差不多。

### 4.2 三个登记时机

| 时机 | 动作 | 是否必填 |
|---|---|---|
| 入库 | 定初始等级（默认 1） | 必填（默认值可一键确认） |
| **还书** | 确认当前等级（可与借出时不同） | **必填**，这是主要采集点 |
| 随时 | 发现破损时手动修改 | 可选 |

### 4.3 变更规则

- 还书时若 `condition_after > condition_before` → **自动写一条 `condition_log` 并绑定该 `loan_id`**
- 战损**只升不降**（除非手工"修补完成"回调，且必须填备注）
- 战损降级/升级都不追责、不扣分——只留痕。**这是设计红线**：系统不评价孩子，只记录事实

## 5. 手表端交互设计（扫描 + 语音）

### 5.1 设计前提

| 约束 | 应对 |
|---|---|
| 1.4 英寸屏，几乎无法打字 | **一切输入靠扫描和语音**，文字只用于确认展示 |
| 孩子操作，容错要低 | 每一步都有大按钮 + 震动 + 满屏纯色反馈 |
| 只手可操作 | 主要按钮放在拇指自然落点（屏幕下半部） |
| 屏幕小、视线短 | 一屏一件事，不超过 3 行字 |

### 5.2 首页

```
┌──────────────┐
│  共 312 本    │
│  在借 18      │
├──────┬───────┤
│ 录 入 │ 借 书  │
├──────┼───────┤
│ 还 书 │ 查 书  │
└──────┴───────┘
      [ 生成报表 ]
```

四个大格子 + 底部一个次要按钮。统计数字实时取自本地库。

### 5.3 场景一：录入（扫 + 说）

**路径 A：有 ISBN（占多数）**

| 步 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点「录入」→ 自动进扫码 | 全屏取景，中央方框 |
| 2 | 扫书背的 ISBN 条码 | 本地查缓存 → 命中则直接带出书名/作者/出版社 |
| 3 | — | 屏幕显示：**书名**（大字）+ 分类（可改） |
| 4 | 语音说「三本」或点 +/− | 册数 = 3，自动生成 3 个内部条码 |
| 5 | 点「好了」 | 写入 3 条 copy，逐张出标签 |

> 目标耗时：**25–35 秒/本**。若 ISBN 查不到元数据 → 转路径 B。

**路径 B：无 ISBN / 扫不出（旧书、盗版、条码磨花）**

| 步 | 操作 | 系统行为 |
|---|---|---|
| 1 | 扫码失败 → 自动提示「说书名」 | 麦克风按钮变亮 |
| 2 | 长按说「夏洛的网」 | 识别为书名文本，显示供确认 |
| 3 | 可选：补说「怀特」 | 作者，可跳过 |
| 4 | 选分类（4 个大色块点选） | 必填 |
| 5 | 说「一本」或点确认 | 生成内部码，`source=voice` |

> **关键**：语音只说"书名"这种开放文本，**不需要识别得很准**——错一两个字，人一眼能改，且这本书以后靠条码识别，书名只影响列表可读性。

**路径 C：同书多册补录**

搜到已有书目 → 点「再加 2 本」→ 直接生成 2 个新条码，不重复录元数据。

### 5.4 场景二：借书（扫 + 说人名）

这是**语音价值最高的场景**——因为人名是最难打字、但候选集合只有 45 个的东西。

| 步 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点「借书」→ 扫码 | 扫书上的 QR/条码 |
| 2 | — | 显示书名；若已借出，直接提示"被王小明借走了" |
| 3 | 长按麦克风说「王小明」 | 语音转文本 → **在 45 人名单里模糊匹配**（见 5.7） |
| 4 | — | 屏幕显示「王小明 借《夏洛的网》」+ 大号确认按钮 |
| 5 | 若匹配到多人 | 列出 2–3 个候选（带姓氏大字），点选 |
| 6 | 点「确定」 | 写入 loan，`due_at = 今天 + 14 天`，震动 + 绿屏 |

**耗时目标：8–12 秒。**

> 若语音不可用（未识别/环境吵）→ 降级为「最近 8 人」头像/姓名快选 + 首字母筛选。**语音是加速器，不是唯一路径**，这一点必须在实现时保证。

### 5.5 场景三：还书（扫 + 说状态）

| 步 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点「还书」→ 扫码 | 反查 active 借阅单 |
| 2 | — | 显示「王小明 · 11月2日还 · 完好」 |
| 3 | 语音说「有点破了」或点选 5 个色块 | 战损等级改为 3 |
| 4 | 点「收下了」 | 结单；若战损升高，自动写 condition_log 并绑定本次借阅 |

> 还书是**唯一强制采集战损的时点**。理由：书在孩子手上待了两周，变化就发生在这段时间；此时不问，以后再也说不清。

### 5.6 场景四：查书 / 场景五：生成报表

**查书**：扫码 → 书名、状态、谁借的、几号还、战损、书架位。一屏放完，只读。

**生成报表**：点「生成报表」→ 提示需连 WiFi → 连上后自动推送 → 显示"已发送到电脑，共 312 册 / 806 条记录"。

### 5.7 语音识别策略（本设计的技术核心）

**不要做开放听写，要做"受限词表 + 模糊匹配"。** 这是这套交互能不能成立的关键。

| 识别目标 | 候选空间 | 策略 |
|---|---|---|
| **人名** | **仅 45 个**（全班名单） | 拼音模糊匹配，容错极高 |
| 册数 | 1–10 | 数字词表 + 谐音（"三/仨/3"） |
| 战损 | 5 个词 | 关键词表（完好/新的/有点旧/破了/很破/烂了） |
| 书名 | 无限 | 开放文本，**允许错字**，人工确认 |
| 书名作者 | 无限 | 开放文本，可跳过 |

**人名匹配算法（四级降级）**

| 级 | 规则 | 例 |
|---|---|---|
| 1 | 完全相等 | "王小明" = 王小明 |
| 2 | **无声调拼音相等** | "wangxiaoming" = 王小明 |
| 3 | 首字母相等 | "wxm" → 王小明 |
| 4 | 拼音编辑距离 ≤ 2 | "王小明" 误识为 "王小明/王晓明/王小明" 均可命中 |

**为什么这套能成立**：语音识别的原始准确率可能只有 70–80%，但候选只有 45 个，经过拼音归一 + 编辑距离后，**命中率可以做到 95% 以上**。而且失败时还有"候选点选"兜底，最差也只是多点一下。

> 对比：如果让人在手表上从 45 个名字里滚动查找，平均要 8–15 秒；语音路径 2–3 秒。这是语音在这个场景的唯一但充分的理由。

### 5.8 语音能力的三种可能形态（需 PoC 确认）

| 形态 | 表现 | 工作量 | 判断 |
|---|---|---|---|
| A. 调用系统/厂商语音输入 | 点麦克风 → 系统弹录音 → 返回文本 | 最小 | ✅ 最理想 |
| B. 应用内录音 + 云端 ASR | 需联网调第三方 ASR | 中等 | ⚠️ 违背"纯本地"，且儿童手表录音权限未必开放 |
| C. 完全不支持 | — | — | ❌ 降级为「快选 + 首字母」，功能仍可用，只是慢 |

> **本设计按 A 设计，按 C 兜底**。无论哪种，人名匹配算法都一样（因为它对"文本从哪来"不敏感）。

### 6.3 导出网关的形态

| 项 | 设计 |
|---|---|
| 运行方式 | 单个 exe，双击运行，控制台窗口显示"等待手表连接 + 本机 IP" |
| 接收 | `POST /api/import`，body 为 gzip 后的 JSON |
| 安全 | 局域网内 + 一次性 6 位配对码（手表端输入，防同网段其他设备乱推） |
| 输出 | 桌面生成 xlsx，自动打开所在文件夹 |
| 留存 | **不落库**：转完即丢弃原始 JSON（可选保留 7 天供重导） |
| 体积 | 预计 < 30MB（Node 打包 + SheetJS） |

> 之所以做成 exe 而不是网页：网页无法接收 POST。要接收就必须有一个能监听端口的进程，exe 是最省心的封装。

## 8. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 手表微应用 | **Vue 3 + Vite + TypeScript**，构建为单文件 H5 | 体积小（< 500KB），启动快；一套代码也能给网关页复用 |
| UI | 手写大按钮组件 + CSS 变量 | 320×320 的界面，任何组件库都是负担 |
| 扫码 | **zxing-wasm**（本地解码）或厂商扫码 API | 本地解码不依赖网络，手表离线也能扫 |
| 语音 | 厂商/系统语音输入 API（PoC 确认） | 见 5.8 |
| 存储 | **IndexedDB（Dexie）** | 无需编译；800 册 + 数千条记录完全够用；沙箱内可用 |
| 拼音 | `pinyin-pro`（约 20KB） | 生成 member 的 pinyin/initials，用于语音匹配 |
| 网关 | **Node 20 + Fastify**，`pkg`/`node-sea` 打包为单 exe | 一个 exe 解决部署，不需要装 Node |
| Excel | **SheetJS（xlsx）** | 生成 xlsx 的事实标准，网关端使用 |
| 二维码兜底 | `qrcode` + 分片重组 | 仅在无电脑时使用 |

**明确不用**：数据库服务、ORM、状态管理库、UI 框架、Docker、云服务、CDN、账号体系。

## 9. 关键流程汇总

### 9.1 建库（一次性）

```
导入名单（复制粘贴 45 个名字 → 自动生成拼音）
  ↓

**建库是最大的一次性成本**，建议按 v0.3 的 6.7.4 三步走：先 150 本冷启动，其余靠"借还即录"和后续补录逐步补齐。**不要等全库建完才上线。**

```

### 9.3 出报表（每周或每月）

```
手表点「生成报表」→ 连 WiFi → 推到教室电脑 → 桌面出现 xlsx → 微信发给老师
```

## 10. 数据安全与容灾（本地存储的必答题）

> 数据只在手表里，意味着**手表丢了/坏了/重置 = 数据全没**。这不是可选项，必须正面解决。

| 措施 | 说明 | 优先级 |
|---|---|---|
| **每日自动快照** | 每次启动时把当前库导出一份 JSON 到 IndexedDB 的 `backup` 分区，保留最近 7 份 | P0 |
| **每次导出即备份** | 推到网关时同时落一份 `.json` 到电脑桌面，老师/学生可留存 | P0 |
| **手表沙箱持久性验证** | PoC 必测：重启、杀进程、断电后数据是否还在（见 11.P2） | P0 |
| **交接前强制导出** | 换届/期末/换表前，必须导出一次并确认文件存在 | P1 |
| **不依赖云端** | 明确告知用户：没有云备份，必须自己保管导出的文件 | — |

**如果 PoC 发现手表沙箱会清数据**，则必须改为"每次操作后立即同步到网关"的在线模式——这会推翻"日常离线"的设计，因此这项 PoC 优先级最高。

## 11. 开工前必须验证的 5 项（S0）

> 这五项任何一项不成立，方案都要调整。建议一次性用真机验完，半天到一天。

| 编号 | 验证项 | 方法 | 不成立的后果 |
|---|---|---|---|
| **P1** | 微应用能否**侧载安装**到这台手表 | 装一个空白 H5 测试页 | 手表端整体不可行，退回"安卓旧手机当采集器" |
| **P2** | IndexedDB 能否**持久保存**（重启/断电后还在） | 写入 100 条 → 重启 → 检查 | **最严重**：必须改为实时同步到网关，日常不能离线 |
| **P3** | 摄像头**扫码**可用（QR + Code128） | 扫 20 张真实标签，记录成功率 | 退化为"手输 9 位码"，录入与借还慢一倍 |
| **P4** | **语音输入**能否拿到文本 | 说 10 个学生姓名，记录识别结果 | 降级为「最近 8 人快选 + 首字母」，可用但慢 |
| **P5** | 能否向**局域网 IP 发 POST** | 推 1 条 JSON 到电脑 | 导出改用二维码分片兜底（1.3） |

**P2 与 P4 是决定性的**：P2 决定架构（离线 or 在线），P4 决定交互（语音 or 点选）。

## 13. 实施计划

| 阶段 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **S0** | **5 项 PoC** + 数据模型定稿 + 交互原型 | 5 项全部有结论；P2/P4 结论决定后续架构 | 1–2 天 |
